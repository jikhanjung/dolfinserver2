# 뒷날 형태를 키로 쓰려다, 윤곽이 천장임을 알았다 (2026-08-27)

> **한 줄로**: 뒷날을 여섯 가지 형식으로 벡터화해 봤는데 전부 AUC 0.59~0.63 에
> 모였다. 그런데 **밝기 경계로 윤곽을 스냅하는 것 하나**가 +0.098 이었다.
> 막고 있는 것은 자가 아니라 **윤곽에 든 정보량**이다.

## 0. 어디서 나온 물음인가

`20260827_001` 25절에서 닮음 정렬을 접으며 이렇게 적었다 — 사람은 뒷날 notch 로
알아보는데 그것이 조각(128px)에서 2~5px 이고 ViT-S/**14** 의 패치는 14px 라,
임베딩이 보는 것은 notch 가 아니라 실루엣과 명암이다.

그러면 **뒷날만 따로 재면 되지 않나.** 실제로 사람이 그렇게 알아보고,
finFindR·CurvRank 등 대부분의 photo-ID 프로그램이 그 방향이다. 제안은 구체적
이었다 — **끝점(apex)에서 뒷삽입점을 긴 축으로 하는 사각형**을 놓고, 긴 변에서
뒷날까지의 거리를 벡터로 만들거나 EFA 를 쓴다.

**방향은 맞다.** 아래는 그 방향이 지금 우리 자료에서 어디까지 가는지를 잰
기록이고, 결론은 **"자를 바꿔서는 안 되고 윤곽을 고쳐야 한다"** 다.

## 1. 무엇을 자로 삼았나

**되풀이되느냐**로 잰다. 진짜 notch 는 같은 개체를 다시 찍으면 같은 자리에 또
있고, 마스크 떨림은 프레임마다 다르다. 둘은 크기도(현의 2~5% 대 1.9%) 공간
주파수도(꼭짓점 간격 7px 대 notch 폭 3~8px) 비슷해서 **필터로는 못 가르는데,
되풀이되느냐로는 갈린다.**

```
같은 개체끼리의 거리  vs  다른 개체와의 거리   →  AUC
좌·우는 안 섞는다 (`normalize` 가 한쪽을 거울처럼 뒤집는다)
같은 날 짝과 날을 건너뛴 짝을 갈라 낸다 — **뒤엣것이 실제로 쓰는 자리**다
```

정답 563조각 중 **뒷날 벡터가 나온 것이 313개**다. 나머지 44%는 `tip_index` 가
끝점을 못 찾거나 뒷삽입점으로 가는 길을 못 골라 **아예 안 나온다.**

## 2. 여섯 형식이 전부 한 자리에 모였다

```
                                          같은 날    날 건너뜀
지금 마스크 · 밑동 현 좌표 · 고정칸           0.559      0.527
지금 마스크 · 곡률 · 늘여 맞춤(DTW)          0.581      0.531
──────────────────────────────────────────────────────────
스냅(±4px) · 뒷날 현에서 벗어난 정도          0.624      **0.625**
스냅 · 곡률 · 늘여 맞춤                      0.634      0.604
모멘트틀 · 곡률 · 돌려 맞춤(원형상관)         0.610      0.615
모멘트틀 · 곡률 · 고정칸                     0.593      0.609
모멘트틀 · EFA 크기 12차                     0.591      0.606
```

축을 바꾸고(밑동 현 → 뒷날 현 → 모멘트틀), 정렬을 바꾸고(고정칸 → DTW →
원형상관), 표현을 바꿔도(좌표 → 곡률 → EFA) **전부 0.59~0.63 이다.**

서로 꽤 독립적인 여섯이 같은 데서 멎으면 **막는 것은 형식이 아니라 입력**이다.

```
입력을 고친 것 (밝기 스냅 하나)   0.527 → 0.625   **+0.098**
자를 고친 것들 (여섯 형식)        0.59 ~ 0.63       ±0.02

                                  **입력이 자보다 다섯 배 세다**
```

## 3. 하나씩 — 무엇을 기대했고 무엇이 나왔나

### 축을 뒷날 현으로 바꾸기 — +0.008

`reid.trailing_edge` 는 **밑동 현**(앞삽입점 → 뒷삽입점)을 축으로 놓고 뒷날을
(x,y) 64점으로 낸다. 제안대로 **끝점 → 뒷삽입점**을 축으로 놓으면 두 가지를
얻는다: 지느러미가 뒤로 눕는 정도가 축에 흡수되어 남는 것이 notch 뿐이고,
차원이 128 → 64 로 준다. 어제 곡선 128차원을 뺄 때 "정답 563조각인데 128차원은
부담" 이라고 적은 그 부담이 준다.

**방향은 맞았는데 폭이 잡음 수준이었다.**

### 늘여 맞추기(DTW) — +0.02

같은 개체·같은 날에도 **뒷날 호 길이가 14.2% 흔들린다.** 고정 64칸으로 견주면
3번 칸이 한 장에서는 notch 이고 다른 장에서는 그 옆 매끈한 데가 된다. DTW 는
그 흔들림을 흡수하라고 넣었다.

거의 안 올랐고, **이유가 나중에 드러났다** — DTW 는 늘였다 줄였다 하지만
**양 끝은 반드시 양 끝에 맞춘다.** 시작점 자체가 밀렸으면 안에서 흡수 못 한다.

### 곡률 — +0.02

CurvRank 가 좌표가 아니라 곡률을 쓴다. 축을 어떻게 잡든 안 변하는 값이다.
창을 3에서 6으로 넓히니 조금 나았다(0.558 → 0.581) — 좁은 창은 마스크 떨림을
그대로 센다.

### 마스크가 notch 를 지우나 — **아니다, 없는 요철을 만든다**

사람이 직접 그린 윤곽(272개)과 모델 마스크를 **같은 상자에서** 견줬다.

```
뒷날 거칢 (현 기준)   사람 0.0122   모델 0.0191   → **모델이 157%**
뒷날 거칢 최대        사람 0.0399   모델 0.0522   → 모델이 131%
모델이 더 거친 상자   195 / 235
```

예상은 "모델이 뭉갰겠지" 였는데 반대였다. 그리고 크기가 하필 —
**진짜 notch 현의 2~5% · 모델의 들쭉날쭉 1.9%.** 얕은 notch 는 마스크 자신의
떨림에 묻힌다.

**한정**: 사람은 클릭으로 그려서 폴리곤이 70점(모델은 191점)이다. "사람이 더
매끈하다" 가 **"모델이 시끄럽다" 인지 "사람이 성기게 그렸다" 인지 이 숫자만으로는
안 갈린다.** 가르려면 사람이 notch 라고 한 자리에서 둘을 겹쳐 봐야 한다.

### 밝기 경계로 스냅 — **+0.098, 유일하게 큰 것**

마스크는 prototype 격자에서 나온다(입력의 1/4 — 640 크롭이면 160×160, 한 칸이
크롭 4px). notch 는 크롭 6~16px 이라 **한 칸 반에서 네 칸**이다. `retina_masks`
가 640 으로 늘려 저장하지만 **늘린다고 정보가 생기지 않는다.**

640 크롭에는 원본 화소가 다 들어 있으니(원본 ~286px 영역을 640으로 편 것), 그
격자를 벗어나 **밝기 기울기가 가장 센 자리로 옮겨 붙였다.** 학습이 없다 —
지느러미는 물 위의 검은 형체라 경계 대비가 세다.

```
폭 ±4px   같은 날 0.624 · 날 건너뜀 **0.625**   ← 가장 좋다
폭 ±6px           0.622          0.609
폭 ±10px          0.602          0.605          ← 넓히면 파도·반사로 뛴다
```

**진짜 경계는 마스크에서 몇 px 안에 있다.**

#### 여기서 창 크기를 한 번 잘못 잡았다

처음에 튐을 막으려고 **5칸 평균**으로 폈다. 그런데 간격이 1.5px 이라 창이
7.5px 이고 **notch 폭이 6~16px** 이다 — 튐을 지우면서 **진짜 notch 도 같이
뭉갰다.** 오늘 내내 문제였던 "잡음과 신호가 같은 크기" 를 그대로 반복한 것이다.

**너비 3의 중앙값**으로 바꿨다. 중앙값은 한 점짜리 튐만 없애고 여러 점이 함께
들어간 계단은 남긴다 — notch 가 그 계단이다. 실측으로도 창 5는 날 건너뛴 쪽에서
0.625 → 0.607 로 내린다.

**아침의 L2 대 L1 과 똑같은 구조다** — 고르게 누르는 것과 튄 것만 골라내는 것은
다른 일이다.

## 4. 내가 두 번 틀렸고 둘 다 측정이 고쳤다

### ① "뒷삽입점은 사람이 검토한 값이라 안정적이다" — **틀렸다**

그 위에서 "그러니 고칠 자리는 끝점(apex)" 이라는 결론까지 냈다. 정규화가
뒷삽입점을 (1,0)에 박아 두어 그 좌표계로는 잴 수가 없으니, **마스크의 모멘트
좌표계**(무게중심·주축·√넓이 — 전부 넓이 적분이라 경계 떨림에 둔감하다)로 쟀다.

```
같은 개체·같은 날·같은 쪽 묶음 43개

  뒷삽입점    흔들림 **0.093**
  끝점(apex)   흔들림 **0.054**   → 끝점이 오히려 0.6배
```

**반대였다.** 그리고 왜인지가 세어 보니 나온다 —

```
정답 563조각 중 사람이 밑동을 직접 그린 것  **237 (42%)**
나머지 326개는 `infer_base`(pose-v1) 제안 그대로
사람이 그린 것만 골라도 0.098 — 전체(0.093)보다 나쁘다
```

격자가 거른 축은 **`base_partial`(짐작이냐)** 이지 **누가 그렸느냐**가 아니었다.
그 둘을 섞어 읽은 것이다. 그리고 사람이 그린 쪽이 더 흔들리는 것도 말이 된다 —
**삽입점은 물에 잠겨 있거나 몸통과 이어져 경계가 없는 자리**라, 사람이 매번
클릭으로 찍으면 그 판단 자체가 사진마다 흔들린다. 모델은 적어도 같은 규칙으로
흔들린다.

`models.py` 의 `base_partial` 주석이 이미 "뒷삽입점이 짐작이면 notch 를 재는 쪽
끝이 흔들린다" 고 적어 두었는데, **짐작이 아니라고 표시된 것들도 흔들리고
있었다.**

### ② "끝점이 병목이니 안 쓰면 된다" — **아니었다**

먼저 논리가 순환이었다. "끝점에서 호 길이 60%까지 자른다" 는 안은 **자를 자리도
배율도 결국 끝점으로 재는 것**이라, 끝점이 흔들리면 둘 다 흔들린다.

그래서 두 끝을 아예 안 쓰는 자를 세웠다 — **모멘트 틀**(기준틀)과 **원형
상호상관·EFA**(시작점을 검출하지 말고 자유 변수로 두는 것). 셋 다 만들어 재니
**0.606~0.615 로 스냅한 기존 방식(0.625)과 같다.**

두 끝이 흔들리는 것은 사실이지만 **그것이 남은 격차의 원인은 아니었다.**

## 5. 그래서 남는 길은 하나 — 윤곽을 더 잘 뽑는 것

```
①  끝점·삽입점 안정화        재 봤다 → **값이 없다**
②  자·정렬·표현 바꾸기       여섯 갈래 재 봤다 → **±0.02**
③  **윤곽 자체를 고치기**    스냅 한 번에 **+0.098**   ← 여기다
```

### 다음에 할 것 — 띠 위에서 다시 분할

뒷날을 따라 **원본 해상도로 512×128 짜리 띠**를 떠서 거기서 다시 분할한다.
그러면 notch 가 30px 넘게 된다 — 조각(128px 정사각)에서 2~5px 이던 것이.

**정답이 이미 있다**: 사람이 직접 그린 윤곽 **272개**. 띠 좌표로 옮기면 그대로
학습 자료이고 새로 그릴 것이 없다.

**한정**: 그 정답이 70점짜리 클릭이라 **그 자체가 notch 를 담고 있는지** 확인이
필요하다. 몇 장을 확대해 원본 위에 겹쳐 보면 안다. 안 담고 있으면 ②의 천장이
거기가 된다.

**하한은 이미 안다** — 학습도 조정도 없는 한 번짜리 스냅이 +0.098 이었으니,
제대로 배운 분할은 그보다 낫다.

### `IoU 0.841` 이 이것을 못 잡는다

분할 성적은 넓이 겹침으로 잰다. 경계가 notch 크기(현의 2~5%)에서 어긋나도 넓이는
거의 안 변한다. **"마스크가 웬만큼은 맞는다" 는 관찰과 "뒷날이 안 되풀이된다" 는
측정이 둘 다 참인 이유가 이것이다.** `seg-v4` 를 낼 때 **경계를 재는 자**를 따로
둘 값이 있다 — 예컨대 사람 윤곽에 대한 뒷날 거칢 비(지금 157%).

## 6. 남은 한정

- **묶음이 43개**다(같은 개체·같은 날·같은 쪽 3장 이상). 중앙값이 몇 묶음으로
  뒤집힐 수 있다
- **모멘트 틀도 완벽하지 않다** — 배가 돌아 원근이 바뀌면 주축도 돈다. 다만
  그건 두 끝에 같이 걸린다
- **모델 제안 밑동이 더 안정적인가**는 못 말한다 — 그 묶음이 3개뿐이었다
- **AUC 0.625 는 여전히 못 쓰는 값**이다. 같은 개체를 반은 맞히고 반은 놓친다.
  이 문서는 "스냅으로 해결됐다" 가 아니라 **"천장이 윤곽임을 확인했다"** 다

## 7. 방법에 대해 남길 것

- **"정의상 안정적" 은 측정이 아니다.** 4절 ①이 그것 하나로 결론까지 틀렸다
- **여러 형식이 한 자리에 모이면 형식이 아니라 입력을 의심한다.** 여섯 갈래가
  0.59~0.63 이었고, 입력을 한 번 고치니 +0.098 이었다
- **필터 창은 재려는 것보다 작아야 한다.** 5칸 평균(7.5px)이 notch(6~16px)를
  함께 지웠다. 그리고 **평균과 중앙값은 다른 일을 한다** — 고르게 누르는 것과
  튄 것만 골라내는 것 (아침의 L2 대 L1 과 같은 구조)
- **싼 반증을 먼저 한다.** 여기 있는 전부가 학습 없이 몇 분~한 시간짜리였고,
  그 덕에 띠 분할에 시간을 들이기 전에 **무엇이 천장인지**를 알았다
