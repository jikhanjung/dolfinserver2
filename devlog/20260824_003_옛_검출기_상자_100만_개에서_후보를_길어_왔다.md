# 003 — 옛 검출기 상자 100만 개에서 후보를 길어 왔다

2026-08-24. **"지금 격자에서 구분 가능한 것은 거의 다 했다"** 는 데서 출발했다.
남은 1,333장을 더 훑어도 수확이 없다면 다음은 둘 중 하나다 — 모델이 후보를
내게 하거나, **후보 자체를 더 가져오거나.** 뒤엣것을 골랐고, 공급원은 옛
운영 DB 의 상자 **999,528개**다.

경로를 끝까지 세워 두 바퀴 돌렸다. `fin.db` 는 한 번도 안 건드렸다 —
`FIN_DB` 로 **사본**을 물려 돌렸다.

## 0. 먼저 자를 고쳤다 — 있지도 않은 키를 재고 있었다

"조각이 안 된 상자 1,270개가 왜 빠졌나" 를 축별로 세었더니 **`뒷날 안 보임`
이 정확히 1,270** 이 나왔다. 빠진 것 전부가 한 축에 걸린다는 게 말이 안 돼
조각이 **된** 쪽에 같은 자를 대 보니 거기도 1,735 전부가 걸렸다.

`rules.resolve()` 에 `edges` 키가 아예 없었다. `s.get("edges")` 가 늘 `None` 을
돌려주고 있었으니 그 축은 **모두 실패**로 세어졌다. `usable()` 이 `edges` 를
판정에서 직접 읽는 것도 같은 이유였는데(주석에 적혀 있다) 그것을 안 읽었다.

**"조각이 된 쪽에 같은 자를 대 보면 0이어야 한다"** 가 자를 재는 자였다.

## 1. 옛 DB 의 이름표는 씨앗이 못 된다

`TODOs` 가 오래 "옛 DB 의 JTA### 189건이 씨앗" 이라 적어 두었다. 세어 보니

```
이름 붙은 상자 277 · 이름 165종
  2개 이상인 이름 60종 → 그중 **날을 건너뛴 것 0종**
  15,000px² 이상 **8개**
```

전부 같은 날이고 거의 다 작다. re-ID 정답은 **다른 날의 같은 개체**라야 하는데
그것이 하나도 없다. 옛 상자는 **후보 공급원**으로만 값이 있다.

## 2. 검토 안 된 상자에서 정말 막히는 축은 `facing` 하나였다

`TODOs` 는 `edges`(뒷날이 가려졌나)와 `base_partial`(뒷삽입점이 짐작인가)에
"대체가 없다" 고 적어 두었다. 그런데 `usable()` 을 읽어 보면 **판정이 없을 때
그 둘을 통과값으로 읽는다** — `edges` 는 없으면 `"both"` 로, `base_partial` 은
빈 값이라 통과다. 실제로 막는 것은 `facing` 과 `cls` 다.

둘 다 이미 대체가 있었다.

- `facing` → `baseline.propose_facing` (사람 156장에서 95%에 적용·정확도 100%,
  애매하면 아무 말도 안 한다)
- `cls` → 분할 엔진이 마스크에 적어 두는 분류 (`Mask.cls`)

**걱정하던 두 축이 안 막고, 안 걱정하던 두 축이 막고 있었다.**

## 3. 넓이 문턱이 코드와 자료에서 갈려 있었다

조각을 다시 만들었더니 701개가 나왔다. v1 은 1,735개다. 문턱을 바꿔 가며 재니

```
MIN_AREA 15,000 → 1,735   v1 과 **집합까지 같다**
MIN_AREA 30,000 →   701
```

`reid/v1` 은 15,000 으로 만들어졌는데 `reid.MIN_AREA` 는 그 뒤에 30,000 이
되었다. 모르고 다시 만들면 **사람이 이미 분류한 조각 1,034장이 격자에서
사라진다** — 화면은 멀쩡하고 수만 줄어든다.

상수를 되돌리지는 않았다. 어느 쪽이 옳은지는 실측할 일이고(`reid.py` 주석이
그렇게 적어 두었다), 지금 필요한 것은 **두 벌이 갈리지 않는 것**이다. 그래서
`reid_chips --min-area` 가 값을 받아 **`items.json` 에 적고**, 이미 있는 격자와
다르면 멎는다.

## 4. `reid_chips` 가 옛 스크립트를 화소까지 재현했다

조각 만들기가 스크립트로만 있어서 `seg` 갈래가 바뀔 때마다 손으로 해야 했다.
명령으로 뽑고 **옛 것과 견줬다**.

```
겹치는 조각 1,735 · facing 같음
조각 화소 차이 최대 0.000000 · 완전히 같은 장수 **1,735/1,735**
임베딩 코사인 중앙값 **1.00000** · 최소 1.00000
```

**덤이 하나 있었다.** 임베딩이 소수점까지 맞아떨어졌다는 것은 `emb.npz` 가
`reid_train` 의 **학습 없는 ImageNet 기준선과 같은 식**이라는 뜻이다. 전에는
"옆에 `backbone.pt` 가 없으니 학습한 게 아닐 것" 이라는 정황이었는데, 이제
계산으로 확인됐다.

## 5. 두 바퀴 — 4일치, 그리고 16일치

```
1바퀴  4일 ×120 → 상자 587(이웃 107 포함) → 마스크 584 → 밑동 571 → 조각  498
2바퀴 16일 ×120 → 상자 2,290(이웃 370)   → 마스크 2,211 → 밑동 2,149 → 조각 1,826
                                                    격자 1,735 → **4,059**
```

새 조각의 57%가 `facing` 을 기하로 짐작하고 `cls` 를 엔진에서 읽은 것이다.
**사람 판정이 하나도 없는 상자가 조각까지 갔다.** m710q CPU 로 2바퀴가 75분.

날은 **안 쓴 날에서 고르게** 뽑았다(2016~2019). 하루에 만 장짜리 날이 여럿인데
통째로 넣으면 그날 바다를 외운다 — `import_boxes --only-dates` 를 붙인 이유다.

## 6. 검색은 후보가 는 것보다 **덜** 나빠졌다

질의(159)와 정답(242조각·35마리)을 고정하고 후보만 늘렸다.

| 격자 | 후보 | 1등 | 첫 정답 | 비례라면 |
|---|---|---|---|---|
| 1,735 | 819 | 18.2% | 20위 | — |
| 2,233 | 1,029 | 17.6% | **25위** | 25.1위 |
| 4,059 | 2,137 | 14.5% | **39위** | 52.2위 |

**4일치에서는 정확히 비례했고 20일치에서는 덜 밀렸다.** 새 조각이 평범한
방해물이면 첫 정답 순위는 후보가 는 배수만큼 밀린다. 1.26배에서는 그대로
맞았는데(25.1 대 25) 2.61배에서는 52가 아니라 39였다.

상위 후보에서의 몫도 정확히 제 몫이다 — 개체별 상위 10 후보 중 새 조각이
**63.4%**, 풀에서의 비율이 **63.5%**.

**검토를 안 거쳐 `edges`·`base_partial` 필터가 빠졌는데도 옛 조각과 구별되지
않는 품질이다.** `TODOs` 가 "전체에 돌리기 전에 그 두 축을 어떻게 할지
정한다" 고 남겨 둔 자리에 대한 답이 여기서 나왔다.

## 7. 아직 못 답한 것 — **지표로는 알 수 없다**

이 2,324장 안에 **진짜 재회가 들어 있는지는 아무도 확인하지 않았다.** 라벨이
없으니 자는 그것을 자동으로 "오답" 으로 센다. 그래서 위의 성적은 **아래로
치우친 자**이고, 참값은 그보다 높다.

확인은 사람만 할 수 있고 볼 것은 적다 — **개체 35마리의 상위 3 후보 105자리
중 70자리가 새 조각**이다(닮음 0.97대, 전부 그 개체가 안 나온 날).

- 몇 장이라도 "같은 애다" 가 나오면 → 이 길이 값을 한다. 규모를 키운다
- 70장이 다 아니면 → **ImageNet 특징으로는 여기까지**다. 옛 상자를 더 가져오기
  전에 대조학습이 먼저다 (`reid_train`, 기준선은 좁은 후보 31.4%)

## 8. 판을 갈아 끼울 수 있게 했다

`/reid` 이 `reid/v1` 을 박아 두고 있었다. 시험 격자를 보려면 그것을 덮어써야
했는데, 그러면 **사람이 지금 쓰고 있는 격자가 사라진다.** `FIN_REID` 로 뺐다.

그래서 지금 두 벌이 나란히 뜬다 — 8900 은 `fin.db`·격자 1,735, 8901 은
사본·격자 4,059. **8901 에서 무엇을 해도 `fin.db` 는 안 바뀐다.**

조각 파일 이름을 화면이 읽는 꼴(`%08d.jpg`)로 맞추는 것도 함께 했다. 안 맞으면
200 이 떨어지는데 격자만 통째로 빈다 — 이 저장소가 가장 자주 겪은 종류다.

## 남은 것

- **상위 3 후보 70장을 사람이 본다.** 이것이 다음 결정을 가른다
- 넓이 문턱 15,000 대 30,000 을 **실측으로 정한다**. 지금은 자료 쪽(15,000)에
  맞춰 두었을 뿐이다
- 좋다고 나오면 **진짜 `fin.db` 에 들이고** 규모를 키운다. 옛 DB 에 15,000px²
  이상 상자가 **400,309개 · 245일** 있다. 2080ti 면 하루에 수천 장이다
