# 001 — 호스트를 안 읽고 "없다" 고 했고, 격자 둘은 짝이 아니었다

2026-09-01. 상태를 보러 열었다가 **호스트 이름을 안 읽고 "묶음이 없다" 고
잘못 말했다**(1절). 그 자리를 채우다가 오늘의 진짜 것이 나왔다 — **격자는
자료가 아니라 그날의 사람 판정으로 걸러진 파생물이라, 뜬 날이 다르면 상자가
다르다**(3~4절).

## 1. 내가 틀린 자리 — 호스트 접두어를 안 읽었다

`HANDOFF` 와 `devlog/20260831_003` 7절이 이렇게 말하고 있었다.

```
묶음 84MB 가 dolfinid:/srv/dolfinserver2/share/reid-2026-08-31/ 에 있고 …
scp <계정>@cdgts.paleobytes.info:/srv/dolfinserver2/share/reid-2026-08-31 .
```

나는 `m710q` 에서 `ls /srv/dolfinserver2/share/` 를 하고 **"디렉토리 자체가
없다"** 고 말했다. **경로 앞의 `dolfinid:` 를 안 읽었다.** 두 줄 다 그 호스트를
적고 있었고, 아래 `scp` 줄은 아예 `cdgts.paleobytes.info` 라고 도메인까지
쓰고 있었다.

저쪽에는 있었다 — 08-31 17:53(KST)에 뜬 **81MB**, `README.md`·`chips.npz`·
`items.json`·`emb-dinov2.npz`·`fin-public.db`·`reid-mini.npz`. 겹치는 세
파일은 오늘 내가 뜬 것과 **sha256 까지 같다.**

> **한 기계에서 없는 것은 "없는 것" 이 아니다.** 이 저장소는 자리가 셋이다
> (m710q `work` · GCP `reid` · GPU). 경로를 보면 **호스트부터 읽는다.**
> 그리고 그 확인은 `ls` 한 번이면 됐다 — 하지도 않고 문서를 고치고 커밋까지
> 했다.

**진짜로 안 되어 있던 것은 하나였다** — 같은 절이 *"224 조각만 여기서
만든다"* 고 적어 놓은 것. 그것은 정말로 안 만들어져 있었고, 그래서 저쪽 묶음
으로는 *"224 가 값을 하나"* 를 물을 수 없었다. 아래는 그것을 채운 기록이다.

## 2. `fin-public.db` — 만드는 법이 저장소에 없다

저쪽 묶음에는 이미 들어 있었다(개체 69 · 개체판정 2,166 · `ip` 0). 그런데
**저장소에는 그것을 만드는 명령도 규칙도 없다** — `fin-public.db` 라는 이름은
devlog 의 그 한 줄뿐이다. 손으로 뜬 것이라 다음에 또 손으로 떠야 하고,
그때 무엇을 빼는지가 사람마다 갈린다.

그래서 규칙을 정해 다시 떴다.

```sql
VACUUM INTO '<묶음>/fin-public.db';      -- 읽기 전용 원본에서 뜬다
UPDATE finseg_identification SET ip=NULL;   -- 828줄
UPDATE finseg_review        SET ip=NULL;   -- 0줄 (옛 줄은 원래 비어 있다)
DELETE FROM django_session;                 -- 6줄
DELETE FROM django_admin_log;
```

`VACUUM INTO` 를 쓴 것은 **원본을 읽기 전용으로만 열려고**다. 검토 화면
컨테이너가 같은 파일을 쓰고 있고, 이 저장소가 되풀이해 적어 둔 함정이 그것이다.
`cp` 로 뜨면 WAL 이 반영 안 된 사본이 나올 수 있다.

`auth_user` 는 **원래 비어 있었다** — 검토 화면이 문 코드 하나로 돌아서
`reviewer` 가 늘 빈다는, `TODOs` 첫 항목이 말하는 그 자리다. 지울 것이 없었다.

뜬 뒤에 상자 10,537 · 판정 6,141 · 개체판정 2,166 · 개체 69 가 원본과 같은 것을
세어 확인했다. **지운 것만 지워졌는지를 세는 것이 이 작업의 절반이다.**

저쪽 08-31 판과 견주니 **정답은 같고**(69 · 2,166) `django_session` 6줄이
남아 있었다. 그것 하나가 오늘 판의 차이다.

## 3. 224 조각을 만들었다 — 그리고 짝이 아니었다

v3 를 뜬 명령에서 `--chip-size 224 --no-look` 만 더했다. 19분(04:35~04:54).

```
조각 7,888 개          ← v3 는 7,912 다
```

**24개가 적다.** 그중 **6개에 개체 판정이 붙어 있다.**

여기서 멈춘 것이 오늘의 값이다. 그대로 `DIR128=reid/v3` 로 돌렸으면 표가
이렇게 났을 것이다.

```
128 (v3)      7,912장 · 정답 1,558   ← 08-27 격자
224 (v3-224)  7,888장 · 정답 1,552   ← 09-01 격자
```

**차이가 조각 크기의 차이인 척한다.** `20260831_002` 가 "개체당 조각 수" 에서,
그 앞이 "이 자가 무엇을 재나" 에서 되풀이 밟은 그 자리다.

### 왜 갈렸나 — 격자는 자료가 아니라 파생물이다

`reid_chips` 는 `reid.usable` 하나로 거른다. 그 축이 전부 **사람이 검토에서
남긴 것**이다 — `cls`·`edges`·`base_partial`·`facing`·넓이. 오늘 판이
이랬다.

```
왜 빠졌나                     수
등지느러미가 아니다          1,206
너무 작다                     553
뒷날이 안 보인다              346
앞쪽을 모른다                 269
뒷삽입점이 짐작이다           197
밑동 두 점이 없다              76
조각·곡선을 못 만들었다          2
```

**전부 사람의 판정에 매달려 있다.** 그러니 판정이 쌓이는 동안 격자를 다시 뜨면
상자가 달라지는 것이 당연하다. 08-27 이후 닷새 사이에 24개가 걸러진 것이다.
`items.json` 은 뜬 날을 안 들고 있어서, **디렉토리 이름 말고는 어느 날 것인지
물을 데가 없다.**

## 4. 버린 길과 고른 길

버린 것: `v3` 를 128 쪽으로 쓰고 24개 차이를 각주로 다는 것. 0.3%니까 넘어갈
만해 보였다. **정답 붙은 것이 6개라 안 넘어간다** — 학습·잼에 들어가는 것은
정답 붙은 1,552장뿐이고, 거기서 6장은 0.4%다. 씨앗 폭이 ±0.6%p 인 자리에서
잴 것이 아니다.

고른 것: **오늘 DB 로 128 을 다시 뜨는 것**(`reid/v3-128`, 18분). 그리고
났다.

```
v3       7,912 · 정답 1,558   (08-27)
v3-128   7,888 · 정답 1,552   (09-01)   ─┐ 상자가
v3-224   7,888 · 정답 1,552   (09-01)   ─┘ 한 개까지 같다
```

**`v3-128 == v3-224` 다** — 집합이 정확히 같다. 이것이 두 몫을 했다.
짝을 만든 것이 하나고, **빠진 24개가 조각 크기 탓이 아니라는 것**이 둘이다.
128 로 다시 떠도 똑같이 빠지므로 원인은 DB 가 움직인 것 하나다.
대조군을 세우면 늘 이렇게 덤이 하나 나온다 — 어제도 그랬다(`20260829_002` 의
에폭 400).

`v3` 는 그래도 묶음에 넣었다. `20260831_003` 의 숫자(얼린 채 49.5 · 1블록
59.4 · 2블록 63.9)가 그 격자에서 난 것이라, **이번 표가 그것과 안 맞을 때
격자가 바뀐 탓인지를 물을 데**가 있어야 한다.

## 5. 조심한 것

- **화면이 보는 `reid/v3` 를 안 건드렸다.** 임베딩을 새로 뽑을 때 `--no-chain`
  을 줬다 — 어제 붙인 손잡이가 바로 제 몫을 했다. 끝나고 mtime 이 08-25·08-27
  그대로인 것으로 확인했다
- **`--no-look`** — 사람이 볼 그림 7,888장을 쓰는 것은 낭비인데, **만들기는
  해야** 어느 상자가 남는지가 같다. 어제 그렇게 만들어 둔 대로 썼다
- **`pgrep -f` 를 안 썼다.** 어제 두 번 걸린 자기-매칭이다(큐가 영영 안 끝나고,
  `pkill` 이 제 셸을 죽였다). 기다리는 것은 **PID 로만** 했다
- **먼저 `--dry-run` 을 걸어 본 것이 메모리 상한을 알려 줬다.** 그것이 8.8GB
  까지 올라갔고 이 기계는 15GB 에 6GB 가 이미 나가 있었다. 두 판을 나란히
  안 돌린 까닭이다

## 6. 묶음 — 옆에 새 것을 두었지, 있던 것을 안 건드렸다

`dolfinid:/srv/dolfinserver2/share/` 에 이제 둘이다.

```
reid-2026-08-31/       81M   08-31 것. 격자 v3 하나 · reid-mini.npz
reid-2026-08-31-full/ 233M   09-01. 격자 셋 · reid-mini 둘(128·224)
  fin-public.db   29M   2절
  README.md             인수인계
  v3/             47M   08-27 격자 — 비교할 데로만
  v3-128/         47M  ─┐ 짝은 이 둘이다
  v3-224/         95M  ─┘ 조각 화소가 3배라 chips.npz 가 크다
```

**있던 것을 덮지 않고 이름을 나눴다.** 겹치는 세 파일이 sha256 까지 같아
덮어도 잃을 것이 없었지만, 레이아웃이 다르고(평평한 것 대 디렉토리 셋)
저쪽이 옛 README 를 보고 있을 수도 있다. 지우는 쪽이 얻는 것은 47MB뿐이다.
보낸 뒤 **양쪽 sha256 을 맞춰 확인했다.**

`-full` 의 README 가 인수인계다. 옛 README 의 좋은 대목(규칙 셋 · 성적표)을
가져오고, **격자가 왜 셋인지**와 DINOv3 가중치를 어디 두어야 `dinov3s` 줄이
도는지를 더했다 (`FIN_MODELS` · 파일 이름 하나 · 라이선스가 계정에 묶여 있어
안 넣었다).

`reid_matrix.sh` 헤더에는 **짝을 맞추라는 줄**을 넣었다. 문서에만 적으면 안
지켜진다는 것이 어제 `20260831_002` 의 결론이었고, 저쪽이 실제로 치는 것은
이 스크립트다.

## 7. 남길 것

- **경로를 보면 호스트부터 읽는다.** 자리가 셋인 저장소에서 한 기계에 없는
  것은 "없는 것" 이 아니다. `dolfinid:` 를 안 읽고 "없다" 고 말했고, **`ls`
  한 번이면 됐을 확인을 안 한 채 문서를 고치고 커밋했다.** 없다고 말하기
  전에 **어디를 봤는지를 함께 말하면** 이 틀림이 안 숨는다
- **격자는 자료가 아니라 그날의 사람 판정으로 거른 파생물이다.** 뜬 날이 다르면
  상자가 다르고, 그 차이는 **비교하려던 축의 차이인 척한다.** 두 격자를 나란히
  놓기 전에 상자 집합이 같은지부터 묻는다
- **대조군은 늘 덤을 하나 낸다.** 짝을 맞추려고 128 을 다시 떴는데, 빠진 24개가
  크기 탓이 아니라는 답이 같이 나왔다
- **`--chip-size 224` 는 아직 아무도 재지 않았다** — 조각만 만들었다.
  재는 것은 GPU 몫이고, 물을 것은 `20260831_003` 8절 그대로다
