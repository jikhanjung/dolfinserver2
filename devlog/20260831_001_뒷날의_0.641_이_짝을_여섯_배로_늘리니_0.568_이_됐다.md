# 001 — 뒷날의 0.641 이 짝을 여섯 배로 늘리니 0.568 이 됐다

2026-08-31. `20260827_003` 의 뒷날 측정을 자료가 는 뒤에 다시 했다. 그리고
그 앞에 **띠 재분할이 시작 전에 막히는 것**을 먼저 확인했다 (`20260829_002`
뒤에 이어지는 일이다).

한 줄로 — **작은 표본이 부풀린 값을 두 번 걷어 냈다.** 하나는 크기가 반으로
줄었고, 하나는 전제가 아예 틀렸다.

### ② "원본 해상도면 notch 가 30px" 이 틀렸다

이게 더 크다. **크롭이 이미 원본을 늘린 것**이었다.

```
원본에서 잘린 한 변   중앙 342px
크롭 한 변           640px
scale               중앙 1.87배  ·  94% 가 확대
```

사진은 5472×3648 로 크다. 그런데 돌고래가 멀어서 지느러미가 342px 이고 밑동
현은 156px 이다. 조각(128px)은 이미 원본의 0.8배쯤이라 **원본으로 가도 1.2배
밖에 안 는다** — 계획이 가정한 6배가 아니다.

꼬리도 봤다. **현 = 잘린 한 변이라고 가장 후하게 쳐도**:

```
notch 2% 가 이만큼 되려면   상자    개체 붙은 것
 ≥  8px                   218 (2.1%)     25
 ≥ 12px                    67 (0.6%)     13
 ≥ 30px                     2 (0.0%)      0
```

30px 을 만들려면 현이 1,500px 이라야 하는데 그런 상자가 43개(0.41%)이고 그중
개체가 붙은 건 **0** 이다. 재학습할 자료가 없다.

**계획서에 적힌 숫자를 자료에서 다시 세지 않았던 것**이 이 항목이 며칠 살아
있었던 이유다.

## 2. 뒷날 AUC 를 다시 쟀다 — 0.641 → 0.568

`20260827_003` 7절의 세 줄을 그대로 재현했다. 조각 511 · 개체 51 ·
**날 건너뛴 같은개체 짝 5,409개** (그때는 그 6분의 1이었다).

```
자                            같은 날   날 건너뜀    2026-08-27
지금 마스크 · 밑동 현 틀 · 좌표   0.528     0.520      0.527
+ 밝기 스냅                    0.555     0.554      0.587
+ 뒷날 현 틀 · 호를 그대로       0.567   **0.568**    0.641
```

**방향은 그대로인데 크기가 반이다.** 스냅 +0.060 → **+0.034**, 호 +0.054 →
**+0.014**. 합이 +0.114 → **+0.048**.

①이 0.527 → 0.520 으로 거의 같게 나온 것이 구현이 맞다는 확인이고, **그 위에서
둘 다 작아졌다.** 그때 한정으로 적어 둔 *"묶음이 43개다 — 중앙값이 몇 묶음으로
뒤집힐 수 있다"* 가 실제로 그랬다.

**발견이 틀린 것이 아니라 크기가 틀렸다.** 스냅도 호도 여전히 값을 한다.
다만 그 둘로 0.641 까지 갔다는 것이 표본의 것이었다.

## 3. 해상도 가설 — 확인되지 않았다

1절에서 "notch 가 원본에서 3~8px 뿐" 이라 했으니, 현이 큰 조각만 모으면 올라야
한다. **안 오른다.**

```
                       같은 날   날 건너뜀   날건너 짝
전부 (현 중앙 189px)     0.567   **0.568**    5,409
현 상위 50% (≥189px)     0.568     0.552      1,528
현 상위 25% (≥236px)     0.574     0.529        414
현 상위 10% (≥285px)   **0.698**   0.480         55
```

**같은 날은 0.567 → 0.698 로 오르는데 날을 건너뛰면 내린다.** 이 갈림은
`20260827_003` 8절이 `rough` 에서 본 것과 **똑같은 신호**다 — 고르는 것이
개체가 아니라 **그 사진의 것**(빛·파도·각도·마스크 잡음)이다. 같은 날에는
비슷하게 나오고 날이 바뀌면 사라진다.

**한정**: 상위 10% 의 날건너 짝이 55개뿐이라 0.480 자체는 폭이 넓다. 확실히
말할 수 있는 것은 **"올라야 하는데 안 오른다"** 까지다. 그래서 명령이 짝
30개 미만인 칸은 **숫자 대신 짝 수를 낸다** — 읽으면 잘못 읽을 값이다.

## 5. 명령으로 남긴다 — `reid_edge`

2026-08-27 에 이 측정을 하고 **스크립트를 안 남겼다.** 오늘 다시 재려니
처음부터 짜야 했고, 그래서 **네 시간 뒤에야** 0.641 이 안 버틴다는 것을 알았다.
자료가 자라면 또 재야 하고, 그때 또 짜면 또 견줄 수 없다.

    python manage.py reid_edge --by-chord

`reid.rear_chord` 도 함께 뒀다 — 좌표를 세우는 식이라 `reid.py` 가 자리다
(`frame`·`normalize` 와 같은 규칙).

**곁들여: 내가 `%` 함정에 걸렸다.** 오늘 아침에 `--help` 를 재는 시험을 붙여
놓고, 저녁에 새 명령의 help 에 `2~5%` 를 적었다. 시험이 `reid_edge` 를 이름까지
짚어서 잡았다. **자를 세워 두면 세운 사람도 잡힌다.**

## 6. 남길 것

- **계획서의 숫자는 자료에서 다시 센다.** "원본이면 30px" 은 아무도 안 세어
  본 값이었고, 세어 보니 3~8px 이었다. 며칠짜리 일에 들어가기 전 한 시간이면
  됐다
- **표본이 작으면 크기를 믿지 말고 방향만 믿는다.** 0.641 은 틀린 발견이
  아니라 **부푼 크기**였다. 방향(스냅·호가 각각 값을 한다)은 그대로 살았다
- **같은 날만 오르고 날을 건너뛰면 안 오르는 것**은 이 과제에서 되풀이되는
  신호다. `rough` 에서 한 번, 오늘 현 크기에서 한 번 — **그 자가 고르는 것은
  개체가 아니라 그 사진이다**
- **자를 남기지 않으면 다음에 견줄 수 없다.** 이번에 든 시간의 대부분이
  지난번 자를 다시 짜는 데 들었다
