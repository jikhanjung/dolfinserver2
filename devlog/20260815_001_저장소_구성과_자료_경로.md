# 001 — 저장소 구성과 자료 경로

2026-08-15. 저장소를 열고 **표본 → 크롭 → SAM2.1 → 검토 → 내보내기 → 학습**
한 바퀴를 끝까지 놓았다. 사람이 검토한 마스크는 아직 하나도 없다.

기존 [dolfinserver](../../dolfinserver) 를 먼저 분석했고(bbox 검출에서 멈춰 있고
게시판·경험치·접근로그가 얹혀 있다), 형제 프로젝트 DiaRUGA 의 SAM2 → 사람 검토
→ YOLO 학습 구조를 참고했다.

## 1. 크롭 단위로 간다 — 실측이 강제했다

DiaRUGA 는 타일링 없이 사진 전체를 `imgsz=1280` 으로 학습했다. **여기서는 그
근거가 성립하지 않는다.**

| | DiaRUGA | 여기 |
|---|---|---|
| 원본 | 2752 × 2208 | **5472 × 3648** |
| 대상 중앙값 | 169 px | **103 px** |
| `imgsz=1280` 에서 | 79 px | **24 px — 뭉개진다** |

원본이 2배 크고 대상이 절반이라 4배 불리하다. 하위 10%(53px)는 12px 로 사라진다.
YOLO 의 작은 물체 기준이 32px 다.

**그래서 상자 둘레를 정사각형으로 잘라 640 으로 편다.** 같은 지느러미가 300px
넘게 들어간다. SAM2.1 의 인터페이스(상자 넣으면 마스크가 나온다)와 모양이 같아
학습한 모델을 SAM2.1 자리에 그대로 끼울 수 있다.

**대가는 검출을 옛 YOLOv5 에 의존한 채로 둔다는 것이다.** 그 검출기가 못 본
지느러미는 이 루프 안에서 표시할 방법이 없다. 첫 바퀴에서는 감수하고 숫자에
한정을 붙인다 (DiaRUGA P04 가 0단계를 버린 것과 같은 판단).

## 2. 이웃 상자를 함께 들인다

크롭이 상자의 2배라 옆 개체의 지느러미가 함께 들어온다 — **표본 2,000개 중
9.2%**. 그 지느러미에 라벨이 없으면 YOLO 는 같은 모양을 어떤 크롭에서는
지느러미라 하고 어떤 크롭에서는 배경이라고 배운다.

- **그냥 버린다** (9.2% 손실) → 버렸다. **무리 지어 있는 개체만 골라 빠진다.**
  정작 어려운 쪽이다
- **사진의 상자를 통째로 들인다** → 버렸다. 2.2배(4,408개)라 검토 부담이 과하다
- **크롭에 들어오는 것만 폐포로 들인다** → 채택. **+318개(16%)** 로 끝난다

옛 DB 에 IoU 1.0 짜리 중복 상자가 3쌍 있었다. 그냥 두면 같은 크롭이 두 벌 생기고
한 지느러미에 폴리곤이 겹쳐 붙는다 — 실제로 라벨 파일에 같은 줄이 두 번 나왔다.
들일 때 거르고 내보낼 때도 한 번 더 막는다.

## 3. 아래 경계 — 밑동 현으로 정했다

SAM2.1 은 **위 윤곽을 아주 깨끗하게 딴다.** 앞·뒷날의 굴곡과 흠집까지 딴다.
흔들리는 것은 **아래쪽뿐**이다 — 지느러미가 등과 만나는 자리와 수면이 겹치는
언저리에서 경계가 사진마다 다르게 잡힌다.

정의가 없어서 생기는 흔들림이라 사람이 먼저 정해야 했다. 셋을 놓고 골랐다.

1. 수면선에서 자른다 → 버렸다. 같은 개체라도 자세에 따라 아래 끝이 달라진다
2. **앞·뒤 삽입점을 잇는 직선** → **채택.** photo-ID 의 fin base chord 와 같고,
   점 두 개면 결정되므로 사람이 고칠 때도 끄는 것이 둘뿐이다
3. 위 윤곽만 쓴다 → 보류. 분할 문제로는 어색하다

### 자동으로 찾으려다 실패했다 — 다시 시도하지 말 것

마스크의 위 옆모습(열마다 가장 위 화소)에서 **기울기가 완만(등)에서
가파름(날)으로 바뀌는 자리**를 삽입점으로 잡으려 했다. 두 번 고쳤고 두 번 다
틀렸다.

- **1차** — 꼭대기에서 바깥으로 걸으며 "완만해지는 곳" 을 찾았다. **꼭대기도
  평평하다.** 점이 거의 다 꼭대기에 찍혔다 (40장 중 양쪽 다 찾은 것 2장)
- **2차** — 양 끝에서 안쪽으로 걸으며 "가팔라지는 곳" 을 찾았다. 마스크의 양 끝은
  뾰족해서 몇 화소는 늘 가파르다 → 27/40 이 아예 못 찾았다

실측한 옆모습이 이유를 말해 준다.

```
타일 3   y : 457 443 429 │ 210 201 205 215 229 248 272 299 331 358 431
      기울기: 0.0 -0.2 -0.8│-41.0  0.2  0.3  0.7  1.0  1.0  1.2  0.7  1.1  2.0
             └─ 등(완만) ┘└앞날(수직)┘└─── 뒷날 ~ 등: 구분되지 않는다 ───┘
```

**앞날은 거의 수직이라 쉽게 잡히지만, 뒷날은 기울기가 0.5~2.2 로 등과 같은
크기다.** 뒷삽입점은 기울기가 아니라 완만한 **곡률** 변화이고 문턱으로는 안
잡힌다. 개체에 따라서는 지느러미와 등이 하나의 매끈한 경사로 이어져 전환점
자체가 없다.

**그래서 사람이 찍는다.** 첫 제안은 상자 아래 두 모서리다 — 대충이지만 **어느
쪽으로도 편향되지 않는다.** 틀린 자동 제안은 사람의 눈을 끌고 가지만 대충의
제안은 그러지 않는다. 300장쯤 쌓이면 키포인트 모델로 제안을 바꾼다.

## 4. 판정을 네 축으로 나눴다

한 칸에 예/아니오 하나로는 안 된다. 각각 아래로 흘러가는 곳이 다르다.

| 축 | 값 | 어디에 쓰나 |
|---|---|---|
| `cls` | fin · fluke · rostrum · other · none | 학습의 분류 |
| `verdict` | ok · fix | 마스크 윤곽이 맞나 |
| `edges` | both · leading · trailing · neither | **re-ID.** 어느 날로 매칭하나 |
| `base_line`·`base_partial` | 두 점 · 참/거짓 | 형태 계측을 낼 수 있나 |

**꼬리지느러미·주둥이를 배경으로 두지 않는다.** 물 위의 검은 삼각형이라
등지느러미와 실루엣이 거의 같은데, 배경으로 가르치면 모델이 "이 삼각형은 아니다"
라는 날카로운 결정을 배워야 한다. 명시적 분류로 주면 훨씬 쉽다 — 시각적으로
가까운 어려운 음성은 배경보다 별도 분류가 낫다. 표본 16장에 제트스키 탄 사람과
새('까치'·'흰등밭종다리' 가 옛 DB 의 `boxname` 에 있다)까지 있었다.

`edges` 는 겹친 개체 때문에 넣었다. **뒤쪽 지느러미는 앞날만 또는 뒷날만 보이는
경우가 많다.** 처음에는 "윗윤곽이 끊기면 통째로 뺀다" 로 잡았다가 버렸다 —
보이는 실루엣은 틀린 것이 아니라 맞는 것이고, 가려진 개체는 검출 모델이 늘
다루는 것이다. **다만 photo-ID 는 주로 뒷날의 결각으로 개체를 가리므로** 어느
날이 온전한지는 남겨야 한다. 앞날도 뒷날도 가린 것(`neither`)만 크롭째 뺀다.

옛 DB 에서 함께 들고 온 것: 개체명 JTA###(re-ID 씨앗), 시민과학자의 `not_fin`
374건·`not_identifiable` 862건. 검토를 다시 받되 제안값으로 띄운다.

## 5. Django ORM 으로 옮겼다

처음에는 `sqlite3` 직접 + FastAPI 로 짰다가 **Django 5.2 + ORM 으로 다시
잡았다.** 파이프라인 스크립트도 전부 management command 가 됐다.

- 스키마의 주인이 하나가 된다 (`finseg/models.py`). 손으로 쓴 DDL 과 ORM 모델이
  둘 다 있으면 언젠가 갈라진다
- dockerize 와 멀티유저가 계획에 있다. `Review.reviewer` 를 문자열로 두었다가
  나중에 FK 로 옮기면 **실제 자료 위에서 마이그레이션**을 해야 한다 — 지금
  `auth` 를 켜 두는 편이 싸다
- 형제 프로젝트들의 배포 표준(`.guides/web/`)이 Django + Docker + SQLite 를
  전제로 쓰여 있다

**멀티유저의 갈림길을 함수 하나로 뽑아 두었다** — `rules.effective_review()`.
지금은 "가장 늦은 판정" 이고, 사람이 늘면 사람마다 최신을 고른 뒤 합의로 간다.
부르는 쪽은 바뀌지 않는다. 이 선택을 여기저기 흩뿌려 두면 그 이전이 불가능해진다.
