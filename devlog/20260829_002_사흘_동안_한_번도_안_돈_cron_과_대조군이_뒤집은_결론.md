# 002 — 사흘 동안 한 번도 안 돈 cron, 그리고 대조군이 뒤집은 결론

2026-08-29. "GCP 자료 가져와서 re-ID 한 번 테스트하자" 로 시작했는데, 가져오는
길이 사흘째 막혀 있었고 재는 길에서는 결론이 한 번 뒤집혔다. 오전 것은
`20260829_001` 에 있다.

한 줄로 — **오늘 배운 것은 둘 다 "재기 전에 무엇을 재는지 보라" 다.**
cron 은 도는 줄 알았고, MLP 는 이긴 줄 알았다.

## 1. 주고받기가 한 번도 성공한 적이 없었다

되받아 오려고 수를 세다 갈렸다.

    GCP (주인)   개체 67 · 개체판정 2,058 · 최근 2026-08-29 00:29
    m710q        개체 53 · 개체판정 1,499 · 최근 2026-08-27 08:24

하루 한 번(06:30) 도는 cron 이 있는데 이틀치가 안 와 있었다. 로그를 열었다.

    ===== 2026-08-27 06:30:01 =====  →  ModuleNotFoundError: No module named 'django'
    ===== 2026-08-28 06:30:01 =====  →  같은 오류
    ===== 2026-08-29 06:30:01 =====  →  같은 오류

    "주고받기 =====" 3번 / "끝 =====" **0번**

건 날부터 한 번도 안 돌았다. `python3 manage.py` 가 cron 의 PATH 에서 시스템
파이썬을 잡아 **첫 줄에서** 끝났다.

### 사흘을 몰랐던 까닭이 둘이다

**오류가 사람 말이 아니었다.** 파이썬 traceback 은 무엇이 없는지는 말해도
무엇을 하라는지는 안 말한다. 로그를 봤어도 "cron 에 venv 가 없다" 로 읽으려면
한 번 더 새겨야 했다.

**그리고 같은 crontab 의 다른 둘은 멀쩡히 돌았다.** `backup_db.py` 와
`pull_gcp_backup.sh` 는 표준 라이브러리(sqlite3)만 써서 시스템 파이썬으로
충분하다. 로그가 세 줄 중 두 줄은 `끝` 을 찍고 있어 **"cron 은 되고 있다" 로
보였다.** 이게 제일 고약한 대목이다 — 부분적으로 도는 것이 아예 안 도는 것보다
알아채기 어렵다.

### 고친 것 — 원인과 "모르는 것" 을 나눠서

**원인**은 `deploy/_venv.sh` 한 자리다. 두 레인이 그것을 읽고 `$PY` 를 쓴다.
찾는 것만이 아니라 **`import django` 까지 해 본다** — 있는 것과 되는 것은
다르고, 갈리는 자리가 정확히 거기였다. 못 찾으면 traceback 대신 무엇을 하라는지
적고 멈춘다.

`exchange.sh` 는 그것을 **ssh 로 저쪽 것을 담기 전에** 읽는다. 1초에 알 것을
1분 뒤에 알 이유가 없고, 담아 온 뒤에 죽으면 저쪽에 임시 파일이 남는다.

**모르는 것**은 다른 병이라 따로 고쳤다. `.guides/web/operations.md` §5 가
이 경우를 그대로 적어 뒀다 — *로그만 남기는 cron 은 검사의 환상이다. 호스트
crontab 에는 `MAILTO` 가 없어서 죽어도 아무 데도 안 간다.* 그래서 상태를
파일에 적고 **`/healthz` 가 읽는다.**

    at=2026-08-29 09:55:02
    ok=1
    stage=끝
    note=개체 65 · 개체판정 2058

**`db/` 옆에 둔다** — 센티넬(`INTEGRITY_FAIL`)과 같은 이유다. `logs/` 는
컨테이너에 안 걸려 있어 거기 두면 화면이 못 본다.

**`degraded`(200)지 `unhealthy`(503)가 아니다.** 화면은 멀쩡히 돌고 판정도
쌓인다 — 낡는 것은 분류기가 배울 자료뿐이다. 503 은 "트래픽 보내지 말라" 는
뜻이라 배포 스크립트의 liveness 대기를 멈춰 세워, 게이트가 아니라 배포 장애가
된다. 이 갈래는 저장소에 이미 서 있었다(백업 센티넬).

트랩은 **`ERR` 이 아니라 `EXIT`** 이다. `ERR` 은 `exit` 을 안 잡는데, 사흘을
죽인 그 경우가 정확히 `exit` 이다 — `_venv.sh` 가 스스로 나간다.

### 재는 것을 "도는가" 가 아니라 "멎은 게 보이는가" 로 잡았다

시험 6개가 재는 것은 레인이 도는지가 아니다. 앞의 것은 cron 이 하는 일이고,
**뒤의 것이 없으면 앞의 것이 멎어도 모른다** — 사흘이 그 증거다.

특히 하나: `test_죽은_채로_멎으면_방금이라도_degraded`. 때가 새것인 것만으로는
안 된다. 사흘을 죽인 모양이 정확히 그것이었다 — 06:30 마다 꼬박꼬박 돌되 매번
첫 줄에서 죽었다.

그리고 `test_파일이_없으면_아무_말도_안_한다`. **안 하기로 한 일을 고장으로
세지 않는다** — 레인을 안 도는 자리에서 늘 `degraded` 를 내면 그 다음부터
아무도 이 자리를 안 본다.

### cron 과 똑같은 환경에서 돌려 봤다

고쳤다고 말하려면 그 환경에서 돌아야 한다.

    env -i HOME=/home/jikhanjung PATH=/usr/bin:/bin SHELL=/bin/sh \
        deploy/gcp/exchange.sh

되받기(+559 판정) · 보내기 · 조각·크롭 rsync 까지 통째로 지나갔다. **처음으로
`끝 =====` 을 찍었다.** crontab 줄에도 `FIN_PY=` 를 적었다 — 없어도 스크립트가
스스로 찾지만, 적어 두면 뜻이 보인다.

## 3. 2층 MLP — 조건이 걸린 자리에서 쟀고, 졌다

`TODOs` 가 걸어 둔 조건은 **"자료가 는 뒤"** 였다. 오늘 걸렸다. `--hidden N`
을 붙여(384→N→개체, ReLU) 같은 폴드·같은 씨앗에서 쟀다.

    같은 5000 에폭
    선형       47.2 ± 0.0 / 73.4 ± 0.0 / 82.9 ± 0.1
    MLP 256    46.2 ± 0.2 / 71.6 ± 0.5 / 83.0 ± 0.3

1200 에폭에서도 46.8 대 45.3 으로 진다. **128·256·512 가 서로 구별이 안 되는
것**도 같은 말이다 — 용량이 천장이면 크기를 따라 움직여야 하는데 평평하다.

씨앗 폭까지 넓다: **선형 ±0.0 대 MLP ±0.2~0.5.** 손잡이가 5배인데 답이 더
흔들린다. 좌현 조각 367장에 손잡이 113,000개는 여전히 과하다.

미룬 근거였던 두 실측(**ViT-B 가 ViT-S 를 못 이김** · **PCA 로 384→256 줄이니
+2.4%p**)이 그대로 유효하다. **천장은 머리가 아니다.**

### 하마터면 반대로 적을 뻔했다

처음에 400 에폭에서만 견줬다. 그때 표는 이랬다.

    hidden 0    44.9 / 70.7 / 81.2
    hidden 128  44.5 / 71.9 / 82.4
    hidden 256  45.1 / 71.7 / 82.8
    hidden 512  44.6 / 71.4 / 82.4

top-5·top-10 이 1%p 넘게 올라 있다. "숨은 층이 후보 줄 세우기를 좋게 한다"
라고 쓰기 딱 좋은 모양이다.

**대조군을 돌리니 뒤집혔다.** 선형에 같은 1200 에폭을 주자 46.8 / 72.2 / 82.5
로 MLP 를 전부 앞섰다. 그 1%p 는 숨은 층이 준 것이 아니라 **선형이 덜 배운
것을 늘어난 손잡이가 메운 것**이었다.

**구조를 바꾸면서 학습량을 안 맞추면 구조 탓을 하게 된다.** 이 저장소가
"성적을 내기 전에 이 자가 무엇을 재나를 물을 것" 이라고 적어 둔 자리에 하나
더 붙는다 — **바꾼 것 말고 함께 움직인 것이 없나.**

## 4. 대조군에서 진짜가 나왔다 — 기본 에폭이 덜 배운 자리였다

    400 (기본)  44.9 / 70.7 / 81.2   ← 기록에 남은 성적이 전부 여기
    800         46.5 / 71.5 / 82.0
    1200        46.8 / 72.2 / 82.5
    2000        47.0 / 72.7 / 82.4
    3000        46.8 / 72.9 / 82.6
    5000        47.2 / 73.4 / 82.9

400 → 800 한 칸에 top-1 이 +1.6%p 뛰고 1200 부터 평평하다. 새 아이디어도
새 자료도 없이 **top-1 +2.3%p · top-5 +2.7%p** — 8/27 에 PCA+L1 로 며칠 걸려
얻은 +3.2/+2.5 에 맞먹는다.

**뿌리는 안내와 기본값이 갈려 있던 것이다.** `exchange.sh` 와
`from_reid_to_work.sh` 는 이미 `--epochs 2000` 을 안내하고 있었는데 기본값은
400 이었고, **재는 명령(`reid_cls --folds 5 --seeds 3`)은 기본값을 썼다.**
누군가 2000 이 낫다는 것을 알고 스크립트에 적어 뒀는데, 그 앎이 기본값까지
가지 않아서 **기록에 남은 모든 성적이 덜 배운 것**이 됐다. 기본값을 2000 으로
올려 한 자리로 모았다.

**정직하게 짚어 둔다** — 에폭을 성적 보고 골랐으니 47.2 를 그대로 "우리 성적"
이라 하면 재는 날 쪽으로 조금 샌 값이다. 안전한 주장은 **"400 은 덜 배운
자리였다"** 까지이고, 쓰는 값은 평평해지는 자리로 잡는다.

없었다. 화면이 조용히 옛 판을 들고 있는 것은 격자(`items.json`)만의 일이
아니었다.

`--fit-all` 이 건드리는 것은 `cls-dinov2.npz` 하나뿐이라 **격자 차례는 안
바뀐다** — `sim` 은 `reid_chips` 가 구워 둔 것이고 `날짜·시간순` 의 `at` 은
DB 에서 그때그때 읽는다. 저쪽에 실어 보낸 뒤 **컨테이너 안에서 직접 읽어**
확인했다.

**화면은 `X @ W.T + b` 로만 읽으므로 `--fit-all --hidden` 은 막아 뒀다.**
그대로 저장하면 칸 수가 안 맞아 화면이 조용히 kNN 으로 떨어지거나 터진다.

## 6. 곁들여 둘 — 둘 다 "글에 박아 둔 것이 낡는다"

**`reid_cls --help` 가 여태 한 번도 뜬 적이 없었다.** help 글에 적은 `+2.4%p`
때문이다 — argparse 는 help 를 `%` 로 포맷한다(`_expand_help`). 이 저장소의
help 는 길고 숫자가 많아 **퍼센트를 적는 것이 예외가 아니라 습관**이라 다시
난다. 모든 명령의 help 가 뜨는지 재는 시험을 붙였고, **`%` 를 찾지 않고
`--help` 를 부른다** — 원인이 아니라 성질을 재야 다른 이유로 깨져도 잡는다.
되돌려서 실제로 잡는 것까지 봤다.

**`우리 42마리 · 23.8%` 가 글에 박혀 있었다.** 오늘 개체는 65다. 하필 그
문장이 *"top-10 을 남과 견줄 때는 개체 수를 함께 적을 것 — 숫자를 그대로 옮겨
적지 말라"* 고 말하는 자리인데, **정작 제가 낡은 숫자를 옮기고 있었다.**
세어서 쓴다.
