# 얕은 조건의 결론 다섯이 깊은 조건에서 뒤집혔다

2026-09-01 ~ 09-02 · jikhanserver (Quadro RTX 8000 ×2, 그중 한 장)

새 GPU 자리에서 인수인계 묶음(`reid-2026-08-31-full`)을 받아 매트릭스와 후속
판을 통째로 돌렸다 — 약 90칸. **m710q 가 CPU 4코어로 정직하게 재어 온 결론들이
대부분 "얕은 조건(얼린 특징·얕은 녹임)에서만 참"이었다는 것**이 하루 만에
드러났다.

최종 1위는 **뒷날 크롭 × DINOv3-B · 10블록 녹임 = top-1 76.8 ± 1.2**
(top-5 90.9 · top-10 94.2). 출발점(얼린 DINOv2-S + 선형, 49.5)에서 **+27.3%p**.
top-10 으로는 전체 조각 DINOv3-B·224·8블록이 95.3 으로 앞선다 — top-1 과
top-10 의 승자가 다른 박빙이다.

## 0. 자 — 모든 칸이 같은 조건이다

5폴드 · 씨앗 3 · **배치 16** · 질의 1,205 · 개체 67 · 관찰일 72.
정답은 `fin-public.db`(2026-09-01 04:32 판 · 개체판정 **2,166**) — 뒷날 이
성적과 비교하려면 `--as-of 2166` 을 붙인다.

### 배치 128 이 −4%p 였다

처음에 묶음 README 의 "48GB 면 128도 된다" 를 따라 배치 128 로 걸었다가
1블록이 56.0 으로 나왔다. m710q 의 59.9 와 갈린 원인을 격자 차이로 의심했지만
**옛 격자 `v3` 로 돌려도 56.0 그대로**였고(두 격자의 상자 차이 24개가 정답에는
하나도 안 걸쳐 있어서 비트까지 같은 결과가 난다), 배치 16 으로 내리니
**59.9 가 소수점까지 재현**됐다. 같은 에폭에서 배치 128 은 걸음 수가 8분의 1이라
덜 배운 것이다. README 의 그 문장은 메모리 이야기지 성적 이야기가 아니었다.
**이 기계에서도 기준은 배치 16 이다.**

## 2. 뒤집힌 것 다섯

전부 같은 패턴이다: **얼린 특징이나 얕은 녹임에서 내린 결론은 깊은 조건에서
안 선다.**

1. **"ViT-B 는 졌다"** (08-27, 얼린 채) → 녹이니 크게 이긴다.
   v2 기준 S→B 가 얼린 채 +1.5 인데 2블록 녹이면 +6.0 (64.3 → 70.3).
2. **"224 조각은 값을 안 한다"** → v2 와 얕은 녹임에서만 참.
   v3-B 를 6~8블록 녹이면 224 가 128 을 +0.6~1.5 이긴다 — 늘어난 토큰
   (16px 패치 기준 8×8 → 14×14)을 **그 토큰을 처리하는 층이 배워야** 쓴다.
3. **"DINOv3 는 DINOv2 를 못 이긴다"** → 같은 크기(S)에선 여전히 못 이기지만
   (곡선만 깊은 쪽으로 밀린다, 꼭짓점 높이는 64.3 으로 동일), **B 에서는
   깊게 녹일수록 벌어져 결국 크게 이긴다** (70.3 → 76.3). v2 는 6블록에서
   무너지는데(50.1) v3 는 같은 자리에서 계속 오른다 — 사전학습의 차이가
   "정확도" 가 아니라 **"몇 블록까지 견디나"** 로 나타난다.
4. **"층별 학습률은 미신일 것"** → 반은 맞고 반은 틀렸다. 얕은 녹임(2블록)에는
   어느 방식(감쇠 0.65/0.8 · 블록만 3e-5)도 손해다. 그런데 **균일 lr 로
   과적합해 무너지는 자리는 살린다** — v2-B 4블록이 65.4 → **72.2** 로 균일 lr
   꼭짓점(70.3)마저 넘었다. 반대로 깊게 배워야 크는 v3-B 에는 족쇄다
   (74.9 → 68.3 · 76.3 → 68.9). **감쇠는 브레이크다** — 미끄러지는 데서만 밟는다.
5. **"해상도가 천장" 의 절반** — 패치보다 작은 notch 는 해상도로 안 풀린다는
   계산(`TODOs`)은 맞았고, 답은 **화소 예산의 재배분**이었다(아래 3절).

## 3. 뒷날 크롭 — `reid/v3-te`

apex·뒷날·뒷삽입점을 포함하는 사각형만 잘라 128 로 다시 세운 격자다.
notch 의 상대 크기가 1.4~1.8배가 된다 — "notch(2~5px)가 패치(14~16px)보다
작다" 는 천장을 **잘라서** 미는 것이다.

- 원료는 `v3-224` 의 `chips.npz` 그대로 (이 기계에 크롭 원본이 없다).
- 좌표는 `items.json` 의 `out`(윤곽 21점 · 0~1 조각 좌표)과 `base` 뿐이다:
  apex = `out` 의 y 최솟값 점, 뒷삽입점 = `base[1]`(앞이 늘 왼쪽이므로),
  뒷날 = apex 오른쪽의 윤곽점들. 셋의 bbox 에 여백 6%를 두르고 잘라
  128×128 로 **비율 무시하고** 늘린다 (일그러짐은 모든 조각이 같이 겪는다).
- 차례·`box_id`·`facing` 을 그대로 보존해 같은 자로 비교된다.

결과는 네 백본에서 방향이 같다 — **꼭짓점을 한두 블록 깊게, 그리고 높게
민다**: v2-S +2.8 (64.3@2 → 67.1@3) · v2-B +1.5 (70.3@2 → 71.8@3) ·
v3-B +0.5 (76.3@8 → 76.8@10). 얼린 채로는 늘 진다(전체 모양을 잃은 값,
−0.7~−3.0) — **크롭은 notch 를 배울 수 있는 백본에게만 값을 한다.**

## 4. `reid_cls` 에 층별 학습률이 붙었다

`--lr-blocks`(머리와 블록의 학습률을 가른다) · `--lr-decay G`(블록 학습률을
꼭대기에서 아래로 G 배씩). 옵티마이저를 파라미터 그룹으로 갈랐지만 **기본값
(decay 1.0)에서는 수학이 한 그룹과 같다** — 1블록 씨앗 1이 고치기 전과
소수점까지 같은 것(59.9)으로 회귀를 확인했다.

## 5. 환경에서 걸린 것 둘

- **torch.hub 다운로드가 SSL 에서 죽는다** (Python 3.14 의 엄격해진 검증 ·
  `Missing Authority Key Identifier`). curl 은 되므로 저장소 zip 과 가중치를
  직접 받아 `~/.cache/torch/hub/` 에 심었다. DINOv2 S·B 는 그렇게, DINOv3 는
  라이선스 링크로 4종(S·S+·B·L)을 받아 `~/models/dinov3/` (`FIN_MODELS`).
- **`reid_matrix.sh` 의 grep 필터가 Traceback 을 삼킨다.** 첫 실행에서
  `--unfreeze` 칸들이 1분 만에 조용히 지나갔는데 로그에 아무것도 없었다 —
  `cls()` 가 성적 줄만 통과시키기 때문이다. 오류가 의심되면 필터 없이 한 칸을
  직접 돌려 봐야 한다.

## 6. 안 잰 것, 그리고 이 숫자의 한계

- **증강** — 인수인계 물음 여섯 중 유일한 미답. 이제 기준선이 크롭 × v3-B
  10블록이므로 그 위에서 잴 것 (`fliplr` 금지는 그대로).
- **두 승자의 앙상블** — top-1 은 크롭이, top-10 은 전체 조각이 앞선다.
  보는 것이 다르다는 뜻이라 로짓 평균이 오를 여지가 있다.
- **76.8 은 실전 성능이 아니다.** 닫힌 판(정답이 카탈로그에 반드시 있다) ·
  카탈로그가 개체군의 6할 · 품질 축으로 걸러진 조각의 값이다. 카탈로그가
  개체군을 덮어 갈수록 이 숫자는 내려가고 그것이 퇴보가 아니다
  (`TODOs` 의 그 항목). **옮겨 갈 것은 숫자가 아니라 방법이다** — 블록 수를
  훑는 것, 크롭, 배치 16, 그리고 `--as-of` 로 세로 비교를 지키는 것.

로그는 이 기계의 저장소 루트 `reid-*.log` 에 있다 (커밋 안 함).
격자 `reid/v3-te` 도 이 기계에만 있다 — 위 레시피로 `v3-224` 에서 다시 만든다.
