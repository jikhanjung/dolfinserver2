# 001 — 검출 한 바퀴를 닫고, 모델을 밖으로 내보냈다

2026-08-23~24. 새 검출기가 찾은 상자 690개를 **전부 검토해** 정밀도가 처음으로
편향 없이 재어졌고(`≥0.40` 87.3%), 그 판정이 `export_detect` 를 지나 **다음 검출
학습으로 이어졌다.** 자료가 1.7배가 되었고 `detect-v2` 가 옛 검출기를 넘었다.
그 뒤로 모델을 ONNX 로 내보내 브라우저에서 돌렸다.

**조용히 새는 자리를 다섯 군데 잡았다.** 전부 같은 종류였다 — 화면은 됐다고
하는데 값이 자료에 안 닿는 것. 다섯 다 **숫자를 견줘서** 잡혔지 화면을 봐서
잡힌 것이 아니다.

## 1. 반쯤 재고 멈추면 낙관 쪽으로 기운다

690개 중 508개만 봤을 때와 전량이 이렇게 갈렸다.

| 문턱 | 508개만 | **690개 전량** | |
|---|---|---|---|
| ≥0.40 | 89.8% | **87.3%** | −2.5pp |
| ≥0.25 | 85.1% | **80.9%** | −4.2pp |
| ≥0.15 | 81.1% | **74.3%** | −6.8pp |
| ≥0.05 | 75.2% | **60.7%** | **−14.5pp** |

왜 그런지는 남은 182개가 무엇이었는지를 보면 안다 — **분할 모델이 마스크를 못
낸 것들**이다. 마스크가 나온 508개는 `fin` 이 75.2%인데 못 받은 182개는 **20.3%**
였다. **마스크가 나오느냐가 "진짜 지느러미냐" 와 상관이 있다.**

그런데 그 182개는 내가 만든 편향이었다. 검토 전에 `infer` 를 먼저 돌린 탓에
마스크가 생긴 508개가 `masks__is_current=True, reviews__isnull=True` 조건에 걸려
**`검토할 것` 대기열로 옮겨 갔고**, 사람은 그쪽을 훑었다. `새 검출` 에는 마스크
없는 182개만 남았다. 저장된 판정이 `box_id` 순으로 쌓이고 conf 는 뒤죽박죽인
것이 증거다 — conf 순이었다면 0.9대부터 내려왔어야 한다.

**"훑다가 헛것이 늘기 시작하는 자리가 문턱" 이 그래서 안 통했다.** 다만
`Box.conf` 를 남겨 둔 덕에 문턱은 나중에 표로 되읽을 수 있었다. 설계가 그것을
의도했고 실제로 값을 했다.

## 2. 새 검출기가 여는 것은 **가려진 지느러미**다

| | `fin` | `tip`(끄트머리만) |
|---|---|---|
| 옛 YOLOv5 | 2,044 | 62 (**3.0%**) |
| 새 검출기 | 419 | 281 (**67.1%**) |

옛것이 못 본 게 아니라 **그 종류를** 못 봤다. 이 한 줄이 오늘 여러 결정의
근거가 된다 — 아래 4절의 축소 필터가 왜 치명적인지도 여기서 나온다.

`rules.py` 가 되돌린 "`edges` 로 크롭 버리기" 규칙을 살려 뒀으면 이 수확의
3분의 2를 규칙으로 버렸을 것이다. 되돌린 판단이 맞았다.

띠로 끊어 보면 문턱이 정해진다: `≥0.40` 87.3% · `0.25~0.40` 64.4% ·
`0.15~0.25` 53.9% · **`<0.15` 39.4%**. 가장 낮은 띠조차 5장에 2장이 진짜라,
"헛것은 키 한 번에 걸러지지만 놓친 지느러미는 걸러낼 기회조차 없다" 를 그대로
대면 `conf 0.05` 를 유지하는 쪽이다.

## 3. 조용히 새던 자리 다섯

전부 **"화면은 됐다고 하는데 값이 자료에 안 닿는다"** 였다.

| 무엇 | 어떻게 드러났나 |
|---|---|
| 점을 끌어도 `polyMoved` 가 안 섰다 | 셋 중 둘이 200 을 받으면서 윤곽만 빠졌다 |
| 판정이 붙었는데 윤곽이 없는 상자 53개 | 대기열 다섯 중 어디에도 안 떴다 |
| 사람이 그린 윤곽을 `label_of` 가 안 셌다 | 대기열이 0인데 `pending` 이 48이었다 |
| 축소할 때 부드럽게 만들었다 | 작은 상자의 확신이 0.36 → 0.17 |
| 모델을 읽는 동안 떨군 사진을 버렸다 | 화면은 멀쩡한데 아무 일도 안 났다 |

### 3.1 점 끌기 — 가장 많이 하는 일에만 깃발이 없었다

`polyMoved`("윤곽을 고쳤나")를 세우는 곳이 셋뿐이었다 — 점 더하기·우클릭
지우기·`Del`. 정작 **점을 옮기는 `dragVertices` 만 비어 있었다.**

두 모습으로 나타났다. 밑동을 안 건드렸으면 "고친 것이 없다" 며 막았고(그나마
보였다), 밑동을 함께 건드렸으면 `baseMoved` 가 문을 통과시켜 **200 을 받으면서
윤곽만 조용히 빠졌다.** 서버가 `polygon_edited` 를 보고 버리기 때문이다 — 그
규칙 자체는 옳다.

```
5991  box 2629  fin  poly=   0  base=1   ← 잃음
5989  box 2794  fin  poly= 129  base=1   ← 남음 (점을 더하거나 지웠다)
5987  box 2791  fin  poly=   0  base=1   ← 잃음
```

**깃발 하나에 기대는 것을 그만뒀다.** `commit` 이 값을 견준다 — 화면의 윤곽이
들어온 것과도 출발 윤곽과도 다르면 사람이 옮긴 것이다. 깃발 세우는 길을 또
빠뜨려도 이쪽이 잡는다.

### 3.2 어디에도 안 뜨던 상자 53개

판정이 붙으면 `검토할 것`·`새 검출` 에서 빠지고, 마스크가 없으면 `엔진 바뀜` 에
안 걸리고, `verdict='fix'` 가 아니면 `교정 대기` 에도 안 걸린다. 화면은 "남은 일
없다" 고 말하는데 `export_yolo` 는 그 상자가 든 크롭을 통째로 뺐다 — **같은
크롭에 걸친 남의 상자까지 함께.**

`교정 대기` 를 만든 것과 똑같은 자리라 같은 방식으로 풀었다: 대기열 하나와
머리말의 숫자 하나(`윤곽 없음`).

### 3.3 그리는 일 자체가 자료에 안 닿고 있었다

`윤곽 없음` 을 다 비웠는데 `pending` 이 48이었다. 전부 **사람이 윤곽을 그린**
상자였다.

`verdict`("이 마스크가 맞나")는 마스크가 있어야 물을 수 있는 말이라 서버가 안
적는다. 그 규칙은 옳다. **틀린 것은 `label_of` 가 그 빈 칸을 "아직 안 봤다" 로
읽은 것이다.** 물음이 아예 다르다 — 엔진이 낸 마스크는 사람이 "맞다" 고 해 줘야
자료가 되지만, **사람이 그린 것은 그 자체가 사람의 판단**이라 다시 물을 것이
없다.

세 번 다 대기열은 0인데 숫자가 안 맞아서 잡혔다. **화면을 봐서 잡힌 것이 하나도
없다.**

## 4. `export_detect` 가 `fin.db` 를 읽는다 — 루프가 닫혔다

오래 끊겨 있던 자리다.

| | 옛것 | 지금 |
|---|---|---|
| 사진 | 2,508 | **4,240** |
| 상자 | 5,532 | **9,795** |
| 사람이 그린 상자 | 330 | **749** |

인정한 상자 419개가 더해지고(옛 검출기가 놓쳐 아무 라벨에도 없던 자리), 아니라고
한 옛 상자 268개가 빠지고(옛 DB 에서는 `fin` 으로 나가던 것), `fin.db` 사진
1,758장이 새로 들어온다.

**`--date` 로 훑은 날의 사진만 쓴다.** 이 자료의 요건은 "그 사진의 지느러미가
빠짐없이 표시돼야 한다" 하나다. 검출기 둘이 훑고 사람이 전량 판정한 날이라야
거기 가깝다. 날짜는 손으로 안 적고 `infer_boxes` 의 run 기록에서 읽는다 —
손으로 적으면 다음에 더 훑고 나서 여기를 안 고친다. 2016-05-07 이 그렇게 빠졌다.

**`val_date` 경고를 새로 붙였다.** 2016-03-15 는 `infer_boxes` 가 훑은 날이라
그날 정답에 그 검출기가 찾은 상자가 섞여 있다. 거기서 **그 검출기의** 재현율을
읽으면 자기 답을 채점받는 것이다 — 같은 함정에 이틀에 네 번 걸렸고, 이번엔
숫자를 내기 전에 걸렸다.

## 5. `detect-v2` — 재현율에서 처음으로 옛것을 넘었다

120에폭 16시간 36분. 최고 mAP50 **0.9637**(77) · mAP50-95 **0.7173**(101).

공평한 날(2016-03-15 · 사진 1,109 · 정답 1,968):

```
검출기                     낸 것    맞힘    정밀도   재현율   못 찾음
옛 YOLOv5 (conf .25)      1,905  1,859   97.6%   94.5%     109
새 검출기 conf 0.05        3,195  1,918   60.0%   97.5%      50
새 검출기 conf 0.40        2,317  1,882   81.2%   95.6%      86
```

**못 찾은 것이 109 → 50개로 반 이하가 됐다.** 지난 바퀴의 `detect-merged` 는
옛것이 놓친 109개 중 84개를 찾으면서도 전체 재현율에서는 못 이겼는데, 이번엔
넘었다.

### `close_mosaic` 의 마지막 10에폭은 두 번 다 값을 안 했다

| | 전체 최고 | 모자이크 꺼진 뒤(111~120) |
|---|---|---|
| `detect-merged` | 0.9599 / 0.6773 (108) | 0.9593 / 0.6765 |
| `detect-v2` | 0.9637 / 0.7173 (77 / 101) | 0.9613 / 0.7164 |

두 run 이 같은 답을 냈다. **`close_mosaic` 을 줄일 근거**가 된다.

곁가지로 여기서 한 번 틀렸다. "지난번 최고가 108에폭이니 모자이크 꺼진 뒤에
최고가 나온다" 고 적었는데 `close_mosaic=10` 은 **111에폭부터** 끄는 것이라
108은 그 전이다. 사용자가 108 < 111 을 짚어 줘서 알았고, 실제 자료를 보니 꼬리
구간은 값을 한 적이 없었다.

## 6. 모델을 밖으로 — ONNX · 브라우저 · 묶음

### 6.1 축소할 때 부드럽게 만들면 작은 지느러미가 사라진다

`finseg/onnxdet.py` 에 전처리·NMS 를 기준으로 짜고 ultralytics 와 대조하다
잡았다. 같은 사진 한 장(DSC_7067)에서:

| 줄이는 법 | 큰 상자 | 큰 상자 | **작은 상자 (29×21px)** |
|---|---|---|---|
| `PIL.resize` BILINEAR | 0.8851 | 0.8460 | **0.1651** |
| `cv2` INTER_LINEAR (학습이 쓰는 것) | 0.8923 | 0.8537 | **0.3612** |
| `PIL.transform` AFFINE+BILINEAR | 0.8923 | 0.8537 | **0.3691** |

**큰 상자는 0.007 차이인데 작은 상자는 확신이 절반이 된다.** 문턱 0.25 에서
그 상자가 사라졌다. 부드럽게 만든 것이 **학습이 본 적 없는 그림**이라서다.

2절이 여기 걸린다 — 이 검출기가 여는 것의 **67%가 끄트머리만 보이는 작은
지느러미**다. 하필 그쪽부터 먼저 사라진다. 큰 지느러미만 보고 "잘 되네" 하면
못 잡는 종류다.

`PIL.transform` 으로 바꿨다. cv2 와 1/255 안쪽으로 일치하고 의존성이 안 는다.
**시험이 cv2 와 직접 견준다** — 닮았다는 짐작이 아니라.

**canvas 도 같은 함정이 있다.** `ctx.imageSmoothingEnabled = false` 로 꺼야 한다.

### 6.2 자를 두 번 잘못 댔다

처음에 `.pt` 와 견줘 "1~2px 어긋난다" 고 읽었다. ultralytics 는 `.pt` 를
**32의 배수로만 채운다**(1280×864). 우리 ONNX 는 정사각 1280 고정이라 애초에
다른 문제를 풀고 있었다. 같은 `.onnx` 를 ultralytics 로 돌려 견주니 사진 8장에서
**좌표 0.26px · 확신 0.008** 안쪽으로 맞는다.

그 사이 "AFFINE 에 반화소 보정이 빠졌다" 고 의심해 넣어 봤는데, 재 보니 보정
없는 쪽이 cv2 와 맞고 넣은 쪽이 크게 어긋났다(평균차 68). 가설이 틀렸고 코드는
안 건드렸다.

분할은 그 교훈으로 처음부터 옳은 자를 댔다 — 크롭 6장에서 **마스크 IoU 평균
0.9932**.

### 6.3 시간을 재는 것도 같은 함정이었다

브라우저 성능을 세 번 잘못 읽었다.

| 잰 값 | 그때 내린 결론 | 무엇이 틀렸나 |
|---|---|---|
| 3947ms | — | LAN 주소로 열어 WebGPU 가 아예 안 켜졌다 |
| 3028ms | "GPU 가 23%밖에 안 빠르다" | 예열 전 |
| 920ms | "네이티브의 135분의 1" | 예열이 한 번으로 모자랐다 |
| **94ms** | | 몇 번 돌려야 자리를 잡는다 |

**예열은 한 번으로 안 끝난다.** 920 → 665 → 94ms 로 셰이더가 몇 번에 걸쳐
컴파일된다. 그리고 94ms 가 되고 나니 **전처리(297ms)가 3배 무거워졌다** —
병목이 뒤집혔다.

WebGPU 는 **보안 컨텍스트에서만** 열린다. LAN 주소(172.x)로 열면 `navigator.gpu`
가 아예 없어 조용히 CPU 로 떨어진다. 화면이 그것을 말하게 했고, backend 도
짐작이 아니라 **WebGPU 로만 만들어 보고 실패하면 WASM 으로** 다시 만들어 되는
쪽을 적는다.

### 6.4 묶음 — 규칙과 가중치를 함께 움직인다

`.onnx` 하나를 세 곳이 쓴다(여기 · 브라우저 · 데스크톱). 6.1 이 보여 준 대로
**전처리가 어긋나도 예외가 안 난다.** `.guides` 가 이미 말한다 — *"복사는
표류하고, 표류를 보고하지 않는다."*

```
bundles/detect-v2/
  model.onnx  seg.onnx  onnxdet.py  MODEL.json
```

상수는 손으로 안 적고 `onnxdet` 에서 읽는다. `rules_sha256` 으로 받는 쪽이
자기 규칙이 그 가중치의 짝인지 확인한다.

`import_detections` 가 그 반대편이다 — 다른 기계가 낸 `scan.json` 을
`infer_boxes` 와 같은 규칙으로 들인다. **`model` 이 없으면 거부한다.** 어느
검출기가 어느 문턱으로 낸 상자인지 모르면 문턱별 정밀도를 되읽을 수 없다.

## 7. NAS 를 날짜별로 폈다 — **완전 라벨의 공급이 끝났다**

| | |
|---|---|
| 관찰일 | **255일** |
| 사진 | **544,585** |
| `detect-v2` 가 쓰는 것 | **28일 · 4,240장 = 0.78%** |

그런데 **안 쓴 227일에 사람이 그려 넣은 상자가 한 개도 없다.** 749개 전부 이미
들어가 있다. 유일한 예외가 2016-03-16(시민과학 판정 1,206건 · `not_fin` 255건)
인데, 그날은 사람이 **거르기만 하고 채우지 않아서** 일부러 뺐다.

그러니 자료를 더 늘리는 길은 **새 검출기로 훑고 사람이 보는 것**뿐이다.

### 전부 돌리는 것은 쉽고, 보는 것은 불가능하다

```
2026-08-18 스캔: 사진 1,812장 → 새 상자 690개 = 장당 0.381
544,585장 × 0.381 ≈ 새 상자 207,000개
```

**20만 개는 사람이 볼 수 있는 양이 아니다.** 690개에 하루가 걸렸으니 산술로
800일이다. 추론은 장당 6.8ms 라 GPU 시간은 한 시간이고 4.9TB 를 읽는 데 하루면
되지만, **거기서 나온 것을 볼 수가 없다.**

그래서 전부 돌리기 전에 줄이는 방법을 정해야 한다. 셋이 보인다.

- **문턱을 올린다** — `≥0.40` 이면 33%만 남고 정밀도 87.3%
- **날을 넓히되 날마다 얕게** — 227일 × 100장이면 새 상자 8,600개쯤이라 볼 만하다.
  지금 20일이 날마다 100장씩인 것이 애초에 그 설계였다
- **마스크가 나온 것부터 본다** — 1절의 실측대로 그쪽이 `fin` 75.2%, 반대쪽은
  20.3%다. 같은 시간에 더 건진다
