# 001 — 재던 것을 화면에 올리는 길을 뚫고, 크롭 레시피를 얼린 자로 잡았다

2026-09-06. `20260905_001` 6절이 2080ti 로 넘긴 **①②** 를 받아 끝냈다.
넘길 때 적어 둔 것은 "학습하고 임베딩을 다시 내라" 였는데, 실제로 걸린 자리는
그 둘이 아니라 **격자와 레시피**였다. 두 번 다 같은 종류다 — **문서에 적힌
숫자를 자료에서 다시 세지 않은 것.**

시간은 이렇게 갔다.

```
①②를 짜고 붙이기          코드 · 시험     — 반나절
격자·의존성을 맞추기        걸린 자리 셋    — 여기서 더 걸렸다
성적을 재고 원인을 잡기      뒷날이 16%p 낮았다
```

## 1. 막혀 있던 것은 "저장할 자리가 없다" 였다

`reid_cls --fit-all --unfreeze` 가 `CommandError` 로 막혀 있었다. 막아 둔
문장이 그대로 이유였다 — 화면은 분류기를 `X @ W.T + b` 한 줄로 읽는데
(컨테이너에 torch 가 없다) 녹인 블록은 그 한 줄로 안 접힌다.

그런데 코드를 읽어 보니 **접을 필요가 없었다.**

```
BB.split(m, N)  →  pre(얼린 앞부분) · tail(뒤 N블록) · keep
tail(h, blocks, aux)  =  m.norm(h)[:, 0]   ← 이것이 곧 임베딩이다
```

`tail` 이 내는 것이 얼린 백본의 `m(x)` 와 **같은 자리**다. 그러니 녹인 블록으로
격자 전체를 한 번 흘려 임베딩을 다시 내면, 그 위의 머리는 **다시 선형 한 층**
이고 화면 코드는 한 줄도 안 바뀐다. `_fit_deep` 이 이미
`torch.nn.Linear(num_features, n_cls)` 를 낸다 — **③은 공짜였다.**

이 등가를 믿고 짠 것이 아니라 재고 짰다. 조각 16장에서 `m(x)` 와
`pre → tail` 의 **최대차가 0.00e+00** 이다. `split` 의 docstring 이 "비트까지
같다" 고 적어 둔 것을 이 기계에서 다시 확인한 것이다.

## 2. 파일이 둘이 된다 — 그리고 하나는 저쪽으로 안 간다

```
cls-fullL.npz         448KB   머리. 화면이 읽는 형식 그대로
cls-fullL.blocks.pt   1.4GB   녹은 블록. **이 기계에만 둔다**
emb-fullL.npz          30MB   ②가 낸 임베딩
```

`.pt` 가 GCP 로 갈 이유가 없다 — 저쪽에 torch 가 없고, 화면이 읽는 것은
`npz` 둘뿐이다. 그래서 `--fit-all` 이 `.pt` 를 곁에 떨구되 **"아직 짝이
아니다"** 를 찍고 다음 명령줄을 그대로 내놓는다. 짝이 안 선 채로 배포하면
화면이 멤버를 조용히 버리는데, 그때는 성적이 아니라 **로그**를 봐야 알 수 있다.

`emb` 칸에 **아직 없는 파일 이름**을 적어 둔 것도 같은 이유다. `cls-fullL.npz`
면 `emb-fullL.npz` — 이름 규칙 하나로 (a)가 낸 것과 (b)가 낼 것이 짝인 줄
알게 했다.

## 3. ②는 캐시하지 않는다 — `_prefix` 가 그 이유를 이미 적어 뒀다

`reid_cls._prefix` 는 **정답 있는 조각만** 캐시한다(1,300장 513MB). 그 자리
docstring 에 "전부 만들면 497초에 3.1GB" 라고 적혀 있다. ②는 격자 전부를
**한 번만** 지나가므로 담을 이유가 없다 — 담으면 그 3.1GB 다. 남기는 것은
1024차원 결과뿐이라 7,912장에 **32MB** 다.

**`sim` 은 안 건드린다.** 녹은 임베딩은 짝인 머리와만 뜻이 있는데,
화면의 `닮은 것끼리` 정렬과 묶음(`group_links`)은 격자의 기본
임베딩(`emb-dinov2.npz`)으로 돈다. 여기서 덮어쓰면 **멤버 하나를 더한 값이
묶는 규칙까지 조용히 바꾼다.** `--emb-only` 의 기본 동작(`_chain`)을 이 갈래
에서만 끈 것이 그것이다.

## 4. 걸린 자리 셋 — 전부 "미리 있을 것" 목록에 없던 것

### ① 의존성이 백본이 아니라 그 저장소의 `hubconf` 에 있었다

```
ModuleNotFoundError: No module named 'torchmetrics'
ModuleNotFoundError: No module named 'termcolor'
```

DINOv3 를 `torch.hub` 로 여는 순간 그 저장소의 `hubconf` 가 **분할 갈래까지**
끌어온다(`dinov3.eval.utils` → `dinov3.logging`). 우리는 백본만 쓰는데도 없으면
그 자리에서 터진다. `requirements-gpu.txt` 에 적었다 — `sam2` 가 선언 안 하는
`huggingface_hub` 을 적어 둔 것과 **같은 종류**이고 같은 자리에 뒀다.

### ② 격자가 안 맞는 것은 차례만이 아니었다

`20260905_001` 6절이 "**격자가 안 맞는다**" 를 `box_id` 차례 문제로 적어 뒀다.
자료를 열어 보니 **조각 화소도 갈렸다.**

```
reid/v3       chip (7912, 128, 128)   ← 화면이 보는 격자
reid/v3-224   chip (7888, 224, 224)   ← 챔피언이 배운 조각
```

224 로 배운 백본에 128 을 늘려 넣는 것은 다른 입력 분포다. 그러니 ②는
"`v3` 차례로 내라" 가 아니라 **"`v3` 상자 7,912개의 224 조각을 먼저 떠라"**
였다. 한 줄로 적어 둔 인수인계가 자료 앞에서 두 줄이 된 것이다.

### ③ 빠진 24개는 자료가 없는 것이 아니라 **버려진 것**이었다

`reid_chips --boxes <24> --dry-run` 하나로 끝났다.

```
왜 빠졌나                수
등지느러미가 아니다        24
```

08-27 에 격자를 뜬 뒤 09-01 사이에 **전부 재판정된 상자**다. 224 로 다시 뜰
대상이 아니라 `reid.usable` 이 마땅히 거른 것이다. 그래서 그 24줄만 128 을
224 로 늘려 채우고 나머지 7,888줄은 `v3-224` 것을 **비트까지 그대로** 옮겼다
(`scripts/make_full224.py` → `reid/v3-full224`, 7,912장).

**버린 것: 격자를 통째로 다시 뜨는 길(`v4`).** 그쪽이 제대로다 — 화면에서
지느러미 아닌 것 24장도 함께 빠진다. 다만 `items.json` 의 **차례**에 조각·크롭·
분류기가 묶여 있어 레인으로 통째로 날라야 하고, 지금 얻을 것은 0.3%다.
**개체가 붙을 일이 없는 24줄을 위해 격자를 흔들지 않는다.**

## 5. 셈이 두 배 넉넉했다 — 그리고 그것을 셈이라고 적어 둔 것이 값을 했다

`20260905_001` 이 "**이 셈을 믿지 말고 한 에폭만 재서 곱할 것**" 이라고
적어 뒀다. 그대로 했다.

```
에폭 1 → 57.4초        에폭 5 → 195.0초
  ⇒ 한 에폭 34.4초 · 고정비 23.1초 (모델 열기 + 캐시 8초 + 저장)
```

| | 셈 (09-05) | 실측 |
|---|---|---|
| ① 한 갈래 20에폭 | 한 쪽당 15~25분 | **12분 (좌우 합쳐)** |
| ② 격자 임베딩 | 멤버당 2~3분 | **2분** |
| 메모리 | 5~6GB | **5.2GB** |

셈이 틀린 것이 아니라 **한 쪽 기준이었다.** 실제로는 좌우가 같은 캐시를
나눠 쓴다 — 캐시가 8초고 그 뒤로는 블록만 돈다. 3절에서 캐시를 만든 값이
여기서 한 번 더 돌아온 셈이다.

## 6. 성적 — 전체는 재현됐고 뒷날이 16%p 낮았다

폴드 5 · 씨앗 1 · `--as-of 2168` · 질의 1,205.

| | top-1 | top-5 | top-10 | 저쪽(09-03) |
|---|---|---|---|---|
| 전체 조각 L · 14블록 | **84.1** | 94.1 | 96.3 | 84.9 (15블록) |
| 뒷날 크롭 L · 16블록 | **67.7** | 86.7 | 91.1 | **84.0** |
| 앙상블 (반반) | 85.6 | 94.7 | 96.5 | **89.2** |
| *(참고)* 얼린 kNN | 28.0 | 59.7 | 71.8 | |

**전체 갈래는 섰다** — 깊이·씨앗·정답 수가 다른 것을 감안하면 84.1 은 84.9 와
같은 자리다. 화면이 지금 쓰는 44.5 에서 **+39.6%p** 이고, 무엇보다 이 숫자는
화면이 내는 것과 **같은 함수**(`reid.ens_logits`)로 낸 것이다.

**뒷날 갈래가 안 섰다.** 그래서 앙상블도 +4.6 이 아니라 +1.5 였다.

## 7. 원인을 18분짜리가 아니라 3분짜리로 잡았다 — 이 절이 요점이다

깊은 학습으로 기하를 훑으면 한 판에 18분이다. 대신 **얼린 선형**을 대리자로
세웠다 — 같은 격자, 같은 폴드, `--unfreeze` 만 뺀 것. 한 판에 **3분**이다.

```
얼린 선형 top-1     전체 조각 55.6        뒷날 크롭 41.4        차이 −14.2
```

`20260902_001` 3절이 **얼린 크롭은 전체보다 −0.7~−3.0** 이라고 적어 뒀다.
−14.2 는 그 밖이다. **학습 설정이 아니라 격자가 저쪽 것과 다르다**는 것이
이 한 줄로 갈렸다.

그 다음은 자를 대는 일이었다.

```
뒷날 bbox 중앙   폭 0.189 · 높이 0.554  (조각 대비)
→ 정사각으로 늘리면  가로 5.29배 · 세로 1.81배
```

`20260902_001` 3절이 말한 **"notch 의 상대 크기가 1.4~1.8배"** 는 **세로
(1.81배)와만 맞는다.** 나는 같은 절의 "비율 무시하고 늘린다" 를 그대로 읽어
가로를 5.3배 뭉갰고, 그러면 뒷날 곡선의 모양 자체가 일그러진다. **한 문서
안의 두 문장이 어긋나 있었고, 자료에서 배율을 세기 전까지 그것을 몰랐다.**

기하 다섯을 얼린 자로 훑었다.

| 기하 | 얼린 선형 top-1 |
|---|---|
| 현행 (가로 5.3배) | 41.4 |
| 여백 25% | 42.2 |
| 왼쪽 더 담기 | 53.4 |
| **비율 유지** | **57.1** |
| 비율 유지 · 224 | 56.8 |
| 왼쪽 더 + 비율 유지 | 57.8 |
| *(견줄 자리)* 전체 조각 | *55.6* |

비율만 지키면 얼린 크롭이 **전체 조각을 넘는다**(57.1 대 55.6) — 저쪽이 적어
둔 −0.7~−3.0 보다도 좋다.

**버린 것 둘.** `왼쪽 더` 가 0.7%p 앞서지만 질의 1,205에서 **8문항** 차이라
잡음이고, 무엇보다 전체 조각과 닮아져 **앙상블의 상보성을 깎는다** —
`20260903_001` 이 "앙상블은 수가 아니라 상보성" 을 이미 재 뒀다. `224 출력` 은
얼린 자에서 이득이 없었다(56.8 대 57.1). 레시피에 가장 가까운 **`비율 유지`**
로 갔다.

## 8. 다시 잰 것 — 멤버가 뒤집혔는데 앙상블은 안 움직였다

`비율 유지` 로 격자를 다시 뜨고 같은 자로 다시 쟀다.

| | top-1 | top-5 | top-10 | 저쪽(09-03) |
|---|---|---|---|---|
| 전체 조각 L · 14블록 | 84.1 | 94.1 | 96.3 | 84.9 |
| 뒷날 크롭 L · 16블록 | **87.6** ← 67.7 | 96.0 | 97.3 | 84.0 |
| **앙상블 (반반)** | **89.0** ← 85.6 | 96.6 | 97.4 | **89.2** |

**뒷날이 +19.9%p 올랐다.** 얼린 자가 가리킨 자리가 그대로 깊은 자에서도
났다(41.4 → 57.1 이 67.7 → 87.6 으로). **앙상블은 89.0** 으로, 씨앗과 정답 수가
다른 것을 감안하면 저쪽 89.2 와 같은 자리다.

그런데 여기서 **읽을 것이 하나 더 나온다.**

```
저쪽:  84.9 + 84.0  →  89.2
여기:  84.1 + 87.6  →  89.0
```

**멤버 하나를 3.6%p 좋게 만들었는데 앙상블은 0.2%p 내렸다.** 저쪽에서는
크롭이 전체보다 **약한** 멤버였는데(84.0 대 84.9) 여기서는 **더 센** 멤버가
됐고(87.6 대 84.1), 그런데도 합은 같은 자리다. `20260903_001` 이
"**앙상블은 수가 아니라 상보성**" 이라고 쓴 것을 반대쪽에서 다시 본 셈이다 —
그때는 "약한 멤버가 +4.6 을 보탠다" 였고, 이번은 "**센 멤버가 더 보태지는
않는다**" 다. 비율을 지킨 크롭이 전체 조각과 **닮아졌기** 때문으로 보인다.

그러니 이 결과를 "크롭 레시피를 고쳐 앙상블이 좋아졌다" 로 읽으면 안 된다.
**앙상블은 제자리고, 대신 단독 최고가 84.9 → 87.6 이 됐다.** 배포에는 그것이
값을 한다 — 멤버 하나만 실어도 87.6 이다.

**안 쫓은 것**: `왼쪽 더` 를 버린 근거(상보성)가 이번 결과로 오히려
흔들렸다. 상보성이 그렇게 중요하다면 **전체와 덜 닮은 크롭**이 앙상블에
더 좋을 수 있고, 그것이 바로 원래의 일그러진 크롭이 하던 일일지도 모른다
(단독 67.7 · 앙상블 +1.5 였으니 그쪽은 아니었지만). **재려면 세 벌을 같은
자로 놓고 앙상블만 견주는 판이 따로 필요하다** — `TODOs` 로 넘긴다.

## 9. 남길 것

- **넘길 때 적은 한 줄이 자료 앞에서 두 줄이 된다.** "격자가 안 맞는다" 는
  차례 이야기였는데 화소도 갈려 있었고, "빠진 24개" 는 자료가 없는 것이 아니라
  **재판정된 것**이었다. 둘 다 명령 한 번(`--boxes --dry-run`, `chip.shape`)
  으로 갈렸다 — **인수인계를 받으면 그 문장들을 자료에서 다시 센다**
- **성적을 재기 전에 격자를 재라, 그리고 그 자는 싼 것이라야 한다.**
  얼린 선형이 41.4 대 57.1 을 3분에 갈랐다. 깊은 학습으로 훑었으면 기하
  하나당 18분이고, 무엇보다 **"학습이 안 된 건가 격자가 틀린 건가" 를
  못 갈랐을 것이다.** 얼린 자는 격자만 본다
- **문서 안의 두 문장이 어긋나면 자료가 심판이다.** "비율 무시하고 늘린다" 와
  "notch 가 1.4~1.8배" 가 같은 절에 있었고 둘은 같이 설 수 없었다.
  배율을 세어 보고서야 뒤엣것이 맞다는 것을 알았다
- **`npz` 는 꺼낼 때마다 통째로 푼다.** 병합 스크립트가 줄마다 `z["chip"][j]`
  를 불러 1.6GB 를 7,888번 풀고 있었다. 16분을 돌고도 안 끝났고, 한 번만
  꺼내게 고치니 **8.7초**다
- **셈은 셈이라고 적어 두면 다음 사람이 잰다.** 09-05 가 "믿지 말고 한 에폭만
  재라" 고 적어 둔 덕에 5분에 갈렸다. 셈이 두 배 넉넉했고, 틀린 게 아니라
  **한 쪽 기준이었다**
- **멤버를 좋게 해도 앙상블은 안 오를 수 있다** (8절). 크롭을 84.0 자리에서
  87.6 으로 올렸는데 합은 89.2 → 89.0 이다. **고칠 곳을 고르는 자가 단독
  성적이면 안 된다** — 그것은 `20260903_001` 이 이미 반대 방향에서 한 말이다
