# 002 — 개체당 조각 수는 지렛대가 아니었다

2026-08-31 저녁. *"자료가 더 있어야 하는 것 아닌가"* 를 재려고 **20장 이상인
개체만** 놓고 돌려 봤다. 대조군이 그것을 뒤집었다. 오전 것은
`20260831_001` 에 있다.

한 줄로 — **곡선을 인과로 읽고 있었다.** 조각이 많아서 쉬운 게 아니라
**쉬워서 조각이 많다.**

## 1. 한 번에 둘이 바뀐다

`20장 이상만` 으로 거르면 개체당 조각이 느는 **동시에 개체 수가 67 → 22 로
준다.** 클래스가 적어지면 그것만으로 성적이 오른다. 그래서 `--min-chips` 와
함께 **개체 수만 같게 맞춘 대조군**(`--sample-ind`)을 붙였다.

```
                        개체    조각    top-1
A 전부                   67   1,300   49.5 ± 0.0
B 20장 이상만            22     965   59.9 ± 0.2
C 아무 22마리 (씨앗 1)   22     402   60.6 ± 0.1
C 아무 22마리 (씨앗 2)   22     398   63.2 ± 0.1
C 아무 22마리 (씨앗 3)   22     474   58.2 ± 0.3
```

**B 가 C 를 못 이긴다.** 조각이 2.4배(965 대 ~420)인데 C 평균(60.7)보다 오히려
살짝 아래다. 10장 문턱에서도 같다 — B10 51.9 대 C10 평균 52.7.

**49.5 → 59.9 의 10%p 는 전부 클래스가 67에서 22로 준 것이다.** 개체당 조각
수가 보탠 것은 0 이다.

## 2. 그러면 곡선의 인과가 뒤집힌다

기록에 이 곡선이 있었고, 1차 목표(`reid.GOAL`)의 근거 절반이 여기서 나왔다.

```
4~9장   11.1%
10~19장 30.6%   ← "문턱이 10에 있다"
20장 이상 33.8%
```

**그건 한 모델 안에서 잰 개체별 정답률**이지 실험이 아니었다. 조각이 많은
개체가 더 자주 맞는 것은 사실인데, 오늘 실험은 **모델에 조각을 더 줘도 안
는다**고 말한다. 그러면 남는 설명은 하나다 — **눈에 띄는 개체가 더 자주 찍히고
더 자주 분류되니 조각도 많다.**

`TODOs` 가 *"지금 42마리를 전부 10장으로 올리는 데 조각 109장이면 된다 —
몇 마리를 40장으로 만드는 것보다 훨씬 세다"* 라고 적어 둔 것이 이 읽기 위에
서 있었다. **그 값이 생각보다 작다.**

### 한정 둘

**대조군의 질의가 어디서 오나.** C 의 22마리에는 1~3장짜리도 섞이는데 그것들은
클래스는 더하면서 질의는 거의 안 낸다 — 그래서 C 의 질의도 결국 잘 찍힌
개체에서 나온다. 다만 **B 는 같은 클래스 수에 훈련 조각이 2.4배인데도 안
이겼으므로**, "훈련 조각이 늘어도 안 는다" 는 그대로 선다.

**대조군 폭이 넓다** — C 가 58.2~63.2 로 5%p 를 오간다. 정직한 진술은
**"B 와 C 가 구별이 안 된다"** 까지다.

## 3. top-1 을 지배하는 것은 개체 수다

```
개체 67 → 49.5
개체 36 → 51.9   (+2.4)
개체 22 → 59.9   (+10.4)
```

**카탈로그가 개체군(100~120)을 다 담아 갈수록 이 숫자는 내려간다.** 그게
퇴보가 아니다. `TODOs` 가 *"성적으로 검수하지 말 것"* 이라고 적어 둔 것이
이것이고, 오늘 그 크기를 쟀다.

**그러면 진척을 무엇으로 읽나.** 저장소가 이미 답을 적어 뒀다 —
`reid_eval --as-of`. 문제를 고정하고 자·자료를 흔든다.

## 4. `--as-of` 를 `reid_cls` 에도 붙였다 — 그리고 자릿수까지 재현했다

그 손잡이가 `reid_eval` 에만 있었다. **재는 명령에 없으면 그 규칙이 안 지켜진다** —
오늘만 두 번 걸렸다(44.9 대 49.5, 0.641 대 0.568).

```
python manage.py reid_cls --folds 5 --seeds 3 --as-of 1338
  → 자료 … 정답 563조각 · 개체 42  ← 개체판정 1,338번까지의 정답
```

**개체 42 · 조각 563 은 2026-08-27 의 상태 그대로다.** 그 위에서 재니
`합 49 493 27.4% 63.5%` 에 `44.9 ± 0.1` 이 나왔다 — `20260827_001` 21절의
표와 **자릿수까지 같다.**

그리고 그 고정된 문제 위에서:

```
epochs 400  (그때)    44.9 ± 0.1
epochs 2000 (오늘)    47.6 ± 0.3      **+2.7%p**
```

**오늘 사흘치 중 처음으로 사과 대 사과인 숫자다.** 나머지는 전부 자료가 함께
자라서 견줄 수 없던 값이었다.

## 5. `/catalog` 에서 조각을 옮긴다

이 화면은 *"한 상자에 두 개체가 섞이지 않았는지"* 를 보는 자리인데, **찾고
나서 고치려면 `/reid` 로 건너가 그 상자를 다시 찾아야** 했다. 눌러서 고르고
(Shift 로 범위) 우클릭하면 옮기기·대표로·빼기가 뜬다.

넣는 길은 `/reid` 와 **같은 API 하나**다 — 판정을 쌓는 규칙이 두 화면에서
갈리면 안 된다. 옮긴 뒤 서버에 다시 안 묻고 DOM 에서 자리와 머리말을 고친다:
물으면 조각 그림을 통째로 다시 받는데 옮긴 것은 한 장이다.

## 6. 남길 것

- **곡선은 인과가 아니다.** 한 모델 안에서 잰 개체별 정답률과 "그 개체에
  조각을 더 주면 나아지나" 는 다른 물음이다. 후자를 물으려면 **거르고 나서
  같은 크기의 대조군**을 세워야 한다
- **거르면 늘 둘이 바뀐다.** `20장 이상` 은 조각을 늘리는 동시에 클래스를
  줄인다. 오늘만 세 번째다(MLP 의 에폭, ArcFace 의 스케일, 그리고 이것)
- **문제를 고정할 손잡이가 재는 명령마다 있어야 한다.** 규칙을 문서에 적어
  두는 것만으로는 안 지켜진다 — `reid_notch --epochs` 가 오늘 아침에 그랬다

## 7. 다음

  개체 수와 날 건너뜀은 그대로 값이 있다
